# 一、需求阶段

## Q1：你这个项目的需求是怎么来的？

### 可能的问题变体

- 「你这个项目的需求是什么？」
- 「为什么要做这个项目？」
- 「谁提的需求？」
- 「你怎么知道用户需要这个？」

### ❌ 常见错误答法

> **「做一个基于知识图谱的 GraphRAG 问答系统。」**

**面试官心里**：「**他把功能当成了需求。**」后面基本不用问了。

**这是最常见、也最致命的错误。**

### ✅ 示范答法（六句，按这个顺序）

> ① 「先说用户。主用户是**反洗钱分析师**——他**懂业务、会用 Excel 和 SQL，但不会写图查询语言**。这个画像直接推出两条硬需求：入口必须是**自然语言**；结论必须是**业务语言加证据**，不能是技术指标。」
>
> ② 「痛点上我梳理了三个，但发现其中一个是**约束**，不是痛点：分析师说不清推理过程。那**不是"改善一点"的问题，是没有它结论根本进不了上报材料**。所以我把它拿出来，放进非功能需求当**硬约束**。」
>
> ③ 「剩下两个里，主痛点是**误报和漏报**——**规则引擎只能看单笔交易，而洗钱的痕迹在路径上**。所以核心论点是：**误报的根源是规则的结构性缺陷，而图能补上这块**。」
>
> ④ 「指标上我踩过一个坑：一开始想把'检出率'当主指标，但痛点是误报——**这两个方向相反**，只看检出率的话**把所有账户标红就能拿满分**。所以主指标定成一对：**固定召回下的精确率** 和 **Precision@K**，并明确**不接受用误报换检出**。」
>
> ⑤ 「边界上我明确不做真实银行对接、不做微调、不做实时流式。就说实时吧——**批处理就能回答'误报率高'这个问题，实时会让复杂度成倍上升而收益不明**。」
>
> ⑥ 「另外我不做反洗钱以外的场景——**聚焦一个场景才能做深**。」

### 🎯 这道题真正在考什么

| 考的是 | 怎么体现 |
|---|---|
| 你会不会**从业务往下讲**（而不是从功能往上讲） | 先讲用户和痛点，再讲功能 |
| 你分不分得清**痛点 / 约束 / 场景** | 「C 是约束不是痛点」 |
| 你懂不懂**指标会被钻空子** | 「标红就能拿满分」 |
| 你有没有**想过边界** | 「聚焦才能做深」 |

## Q2：为什么现有规则引擎不行？（核心归因）

### 这道题是**必考**的，而且一追问就见真章

### ✅ 因果链（背这一条，不要背结论）

```text
① 洗钱的手法本质是「把痕迹打散」——拆金额、绕账户、拉长时间
        ↓
② 规则只能判断「单笔交易」这一个点
        ↓
③ 所以手法一打散，单笔看全都正常 → 规则必然漏
        ↓
④ 为了补漏，就只能加更多规则 → 规则越来越多 → 但结构性漏检还是漏
        ↓
⑤ 但「打散」的过程本身，在图上会留下一个形状：环路、团伙、枢纽
        ↓
⑥ 所以：看单笔没用，要看结构 → 这就是「图」必须存在的理由
```

### ✅ 讲这条链时配的例子（一定要说例子）

> 「有人要洗 100 万。他拆成 20 笔、每笔 5 万以下，从账户 A 转给 B、C、D，再互相转几手，
> 最后汇到他控制的另一个账户 E。
>
> **规则引擎看到的是**：20 笔『5 万以下、账户间正常转账』——**全部无异常**。
> **图看到的是**：钱从 A 出去、绕一圈、回到 E，**而 A 和 E 是同一个人控制的**——**这是一个回流环路**。」

**例子比任何解释都有力。** 面试官听完这个例子，就知道你真的懂了。

### 🎯 加分点

如果对方问「那规则为什么会越来越多」：

> 「因为**每发现一个漏报就补一条规则**——这是**打补丁式修补**。
> 治标不治本，因为**单笔规则永远看不到路径**。」

### ⚠️ 一个致命用词错误：不要说「图的规则」

> ❌ 「用**图的规则**他就绕不开了」

**面试官立刻会问**：「图**的规则**是什么规则？那它不还是规则吗？不还是能绕开吗？」
→ **卡住。**

**正确说法**：**不是"图的规则更严"，是"检查的对象变了"。**

### ✅ 核心区别：规则看「点」，图看「形状」

| | 规则 | 图 |
|---|---|---|
| 检查什么 | **单笔交易的属性**：金额、时间、国家、频率 | **关系的结构**：绕了几手、回到哪、和谁有关 |
| 能改吗 | ✅ **能**——拆金额、换时间、拆分账户 | ❌ **改不了** |
| 为什么 | 这些是**交易的表面属性** | 结构是**洗钱行为的副产品** |

### ✅ 为什么图「绕不开」（这是最关键的推理）

```text
要躲开「单笔金额」这条规则 → 必须把大钱拆成小钱
        ↓
拆成小钱 → 必然产生「多笔」交易
        ↓
多笔交易 → 必然涉及「多个账户」
        ↓
多账户之间转账 → 必然形成「路径」和「形状」
        ↓
而「形状」恰恰是图要检查的东西
```

> **打散痕迹这个动作本身，就留下了形状。**
> **要躲开图，只有一种办法——不洗钱。**

### ✅ 一个记得住的类比

> **规则像查身份证——你可以伪造。**
> **图像查「你和谁来往」——你要办成事，就必然要和人接触，这个关系藏不住。**

（对应你的运维背景：**防火墙按端口封，攻击者换端口就绕过了；
但流量行为分析看的是「这个连接的行为像不像攻击」，换端口没用。**）

## Q3：你的指标是怎么定的？

### ⚠️ 先分清三个词（这是高频追问点）

```
召回率 Recall    = TP / (TP + FN)     ← 分母是「所有真的洗钱」
精确率 Precision = TP / (TP + FP)     ← 分母是「所有报出来的警」
误报率 FPR       = FP / (FP + TN)     ← 分母是「所有正常交易」
```

**`1 − 精确率` 和 `FPR` 不是一回事**——分子一样（都是 FP），**分母不同**。

### 数字例子（记住这个，随时能讲）

1000 笔交易，10 笔真洗钱，系统报 100 条警：

| | 实际洗钱 | 实际正常 |
|---|---|---|
| 报警 | TP = 8 | FP = 92 |
| 不报 | FN = 2 | TN = 898 |

| 指标 | 结果 |
|---|---|
| 召回率 | 8/10 = **80%** |
| 精确率 | 8/100 = **8%** |
| **1 − 精确率** | **92%** |
| **FPR** | 92/990 = **9.3%** |

**差了十倍。** 原因：**正样本极度稀少**（洗钱占比极低），
所以 `TP+FP`（报警数）很小，而 `FP+TN`（正常交易数）极大。

### ✅ 关键表述（背这一句）

> 「**AML 行业口语说的「误报率」，指的是 `1 − 精确率`，不是统计学的 FPR。**
> 在洗钱这种**极度不平衡**的数据上，**两者能差一个数量级**。」

### ✅ 为什么必须报两个指标（用反例讲，最有说服力）

**一个什么都不报的系统：**

| 指标 | 值 |
|---|---|
| 召回率 | **0%** |
| FPR | **0%** ✅ 完美！ |
| 精确率 | 无意义（分母为 0） |

> 「**一个什么都不报的系统，误报率是 0，看起来完美——但它一点用都没有。**
> 所以只报一个指标一定会被骗：
> **报低误报** → 有人可以「什么都不报」拿满分；
> **报高召回** → 有人可以「全部标红」拿满分。
> **必须两个一起报，而且其中一个要固定在合理水平上。**」

### ✅ 最终指标设计

| 指标 | 回答的问题 | 视角 |
|---|---|---|
| **固定召回下的精确率** | 如果不许漏，误报会多到什么程度 | 合规 / 监管 |
| **Precision@K** | 分析师一天看 K 条，效率如何 | 业务 / 人力 |

**两个指标来自同一个排序，只是切点不同**：
取前 K 个 → Precision@K；放宽到召回 90% → 另一个。

**→ 由此推出一条硬性设计约束：系统必须输出可排序的分数，不能只输出「可疑/不可疑」。**

## Q4：你的项目边界在哪？

### ✅ 答法（每条都要带理由）

> 「我明确划了边界：
> **不碰真实银行系统**——我没有生产数据权限，这个项目验证的是**方法**不是接入；
> **不做微调**——FDE 场景以**集成与调优**为主，训练不是重点；
> **不做实时流式**——批处理就能回答『误报率高』这个问题，实时会让复杂度成倍上升、收益不明；
> **不做自动上报**——上报是**合规责任，必须由人做**。但**正因为要由人做，系统必须把证据准备到人可以直接用的程度**，所以证据回链是 P0；
> **不做反洗钱以外的场景**——**聚焦一个场景才能做深**。」

### 🎯 加分点

「聚焦才能做深」——**把"范围小"说成优点**。

## Q5：为什么用图？（和 Q2 的区别：Q2 问"为什么规则不行"，Q5 问"为什么图行"）

### ✅ 答法

> 「因为**洗钱的痕迹不是一笔交易，是一个形状**。
> 拆分留下的是『一对多再汇总』的形状；回流留下的是**环路**；团伙留下的是**紧密子图**。
> **这些形状在单笔交易里根本不存在，只有在图上才存在。**
>
> 而且向量检索也解决不了——向量比的是『意思像不像』，
> 但『跟 A 隔了三层的账户有哪些』**不是像不像的问题，是连不连得通的问题**。」

# 二、设计阶段

## Q6：你这个系统的架构是什么？

### ✅ 一句话版（**先给这句，再展开**）

> 「**图负责「发现异常结构」，向量负责「解释它像哪种已知手法」，
> Agent 负责「自己决定先查什么」，最后每条结论都能回链到原始交易。**」

### ✅ 五层展开

```text
⑤ 交互层   自然语言提问（分析师不会写查询语言）
④ Agent    自己拆解：取邻域 → 找环路 → 匹配手法 → 解释
③ 检索融合  ★GraphRAG★ 图检索 + 向量检索 + 图算法 → 拼成上下文
② 图存储   Neo4j（十万节点 / 百万边）+ 向量库
① 数据     交易流水 + 账户映射 + 模式标签
```

### ✅ 必答的一句：**融合不是加权排序**

> 「很多人以为 GraphRAG 的融合是『两路检索结果加权排序』——**不是**。
>
> **真正的融合是把三种异构证据拼成模型能用的上下文**：
> **结构化事实**（谁转给谁、多少、何时，来自图）、
> **算法判断**（环路长度、社区紧密度）、
> **语义知识**（相似手法描述，来自向量）。
>
> **三者互补**：只有事实→模型不知道该叫什么；只有语义→不知道眼前有没有；
> 只有算法分数→有分数没解释，**分析师不敢信、写不进报告**。」

---

## Q7：图是怎么建模的？（三个关键决策）

### ① 账户主键用「银行 + 账号」

> 「**因为账号在不同银行之间会重复。** 只用账号做主键，
> 招商银行的 `1234567` 和 中国银行的 `1234567` 会被合并成同一个节点，
> **图上凭空多出不存在的资金路径，直接制造假阳性**。」

### ② 「所属实体」既做属性、又做关系

> 「**同一个事实做属性还是做关系，取决于它要不要参与路径查询。**
> 属性用于展示；关系用于**路径查询**——模式『同一实体的多个账户互转』
> 必须靠 `(Entity)-[:CONTROLS]->(Account)` 这条边才问得出来。」

### ③ 同一对账户的多笔转账**不聚合**

> 「因为可疑模式里有**时序特征**——『快进快出』、固定间隔的分层转账。
> 聚合了时间就丢了，**这两类就检测不了**。
> 代价是边数到百万级——**所以我的规模指标是被建模决策推出来的，不是拍脑袋定的**。」

## Q8：为什么不让 Agent 直接生成 Cypher？

> 「**不做，三个理由：**
> **不可控**——可能生成全图扫描，**直接打破 30 秒约束**；
> **不确定**——同一问题生成不同查询，**违反可复现**；
> **不可审**——查询无法预先审计，**而这是金融系统**。
>
> 替代方案是**受控工具**：只能调预定义的 4 个工具，
> **参数上界由服务端强制校验，不是靠提示词约束**。」

**🎯 联系既有经验**：「这个思路我在 HS Code 项目里用过——**用 MCP 封装检索工具**，不让模型自由查库。」

---

## Q9：Agent 的工具怎么设计的？

> 「**第一，分层，不是全细也不是全粗。**
> 全细粒度的话 Agent 要把步数花在逐个调用上，**很可能步数耗尽还没给结论**；
> 全粗粒度的话 Agent 没有编排空间，**退化成调一次函数**。
> 所以做成**「一次侦查 + 按需验证」**——和人一样，先扫全局再深挖。
>
> **第二，每个参数上界都对应一条非功能需求。**
> `hops ≤ 3` 因为邻域随跳数指数增长；`max_length ≤ 8` 因为找所有环是组合爆炸。
> **上界不是保守，是必须。**
>
> **第三，我区分「确认没有」和「没查到」**，还加了 `truncated` 字段——
> 混在一起会让 Agent 把『路径太长没找完』误判成『两者没有关联』。」

**🎯 真实经历（很有杀伤力）**：

> 「工具粒度这个坑我踩过。上一个项目里诊断工具一次只能查一个传感器，
> Agent 把 4 步预算全花在逐个查询上，**压根没走到给结论**，跑出 0% 检出率。
> **看起来像『Agent 能力不行』，实际是工具设计的锅。**」

---

## Q10：怎么保证 Agent 一定会给结论？

> 「**预留最后一步做强制产出。** 前 N-1 步自由侦查，
> **第 N 步无论查到什么都必须产出结论**：是否可疑 + 置信度 + 证据 + 还缺什么。
> **『未发现异常』也是有效结论，不是失败。**
>
> 为什么重要——**「什么都没找到」和「根本没给答案」是两件完全不同的事**：
> 前者是**能力问题**（可量化）；后者是**工程缺陷**，会让**所有指标失真**——
> 它同时压低检出率，又虚假地压低误报率。
>
> **我在产线项目里正是被后者坑过**：15/50 个案例耗尽步数没给答案，
> 却被统计成『无异常』。所以修复后我把它写进验收标准：
> **未产出结论占比必须为 0%**。」

---

## Q11：任务怎么拆、排期怎么定的？

> 「**第一，评测真值先行。** 数据集自带模式标签，我在第一个里程碑就建好真值和指标框架，
> 之后**每完成一个模块立刻接入评测**——图算法做完有检测层数字，
> 检索做完有消融数字，Agent 做完有端到端数字。
> **这样哪里掉了能立刻定位到层。**
>
> **第二，风险最大的放前面。** 数据能不能用是最大不确定性，第一阶段就验证。
>
> **第三，排期留缓冲。** 我排 30 天，按 40 天报——
> 因为我做过 6 个生产项目，**知道数据准备和联调最容易超期**。」

**🎯 加分**：「我还做了**需求追踪矩阵**——每个需求都能指到『由哪个设计满足、由哪个测试验证』。」
