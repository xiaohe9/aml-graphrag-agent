# 架构决策记录（ADR）

> **ADR = Architecture Decision Record（架构决策记录）**
>
> 它记录的不是「我选了什么」，而是「**我还考虑过什么、为什么不选**」。
> **面试官问"还考虑过什么方案"时，你翻这一页就有答案。**
> 这是最容易被忽略、又最能体现深度的一份文档。

| 编号 | 决策 | 状态 |
|---|---|---|
| ADR-0001 | 转账建模为「边」而不是「节点」 | 已接受 |
| ADR-0002 | 本期不做「担保 / 持股 / 任职」关系，P5/P6 推迟 | 已接受 |
| ADR-0003 | 向量库存「已知洗钱手法的描述」，不存交易文本 | 已接受 |
| ADR-0004 | **数据源由 IBM AML 完整集改为 AMLSim 示例集，并据此修正三处需求** | 已接受 |

# ADR-0001：转账建模为「边」而不是「节点」

---

## 状态

**已接受**（2026-XX-XX）

---

## 背景

系统需要构建资金交易网络图，用于检测洗钱中的**资金回流环路**和**可疑团伙**。

一笔转账天然涉及两个账户，但它自身也带一堆属性：
金额、时间、币种、渠道、用途备注……于是产生一个建模分岔：

- **方案 A**：转账作为**边**（账户是点）
- **方案 B**：转账作为**节点**（账户和交易都是点）

---

## 决策

**采用方案 A：转账建模为边。**

```cypher
// A：转账是边
(账户A) -[:转账 {金额: 50000, 时间: "..."}]-> (账户B)

// B：转账是节点
(账户A) -[:发起]-> (交易X {金额: 50000, 时间: "..."}) -[:收款]-> (账户B)
```

---

## 理由

### 1. 核心问题是「路径」问题（**最主要理由**）

我们要回答的核心问题是：**「钱有没有绕一圈回到起点？」**

这是典型的**路径查询**。交易作为边时，一笔转账 = 一条边，
资金链 = 边的序列，**查环路是最自然的图遍历**。

若交易变成节点，每次查询都要**多跳一步**（`账户→交易→账户`），
且环路的判定要在「账户-交易」交替的二分图上做，**语义和实现都更复杂**。

### 2. 我们不需要给「交易」挂关系

需要给交易变成节点的真实场景是：

| 需求 | 需要 B 吗 |
|---|---|
| 记录金额、时间、币种、渠道 | ❌ 不需要——**边的属性就够了** |
| 记录「这笔转账用的哪台设备 / 哪个 IP」 | ✅ 需要 |
| 处理「一进多出」并当成**一件事** | ✅ 需要 |
| 双时间轴（发生时间 vs 记录时间） | ✅ 需要 |

**这四项都在我们的范围之外**：
- 设备/IP 关联属于**反欺诈**问题域（O6：不做反洗钱以外的场景）
- 一进多出可以用多条边表达，虽然不如事件节点优雅，但**满足我们的检测需求**
- 双时间轴属于监管审计需求，本项目不涉及

### 3. 规模检验通过

| 建模 | 节点数 | 边数 | vs 规模要求（十万节点 / 百万边） |
|---|---|---|---|
| **A** | 账户+人+公司 ≈ **10 万** | 转账+持股+… ≈ **100 万** | ✅ **正好** |
| B | 10万 + 100万交易 = **110 万** | 200 万+ | ❌ **超 10 倍** |

---

## 考虑过的替代方案

### 方案 B：交易作为节点

**放弃原因**：
1. **语义上更重**——把「事件」和「实体」混在同一层，查询时要在两类节点间交替跳转；
2. **规模超规格 10 倍**（见上表），会破坏已定的非功能需求；
3. **我们不需要它提供的三项能力**（设备/IP 关联、事件化的一对多、双时间轴）。

**但它不是"错"的方案**——在真实金融图系统中它是常见做法。见「什么情况下要重新审视」。

### 方案 C：混合——图存结构，关系表存明细

**这是真实系统常见做法**：图负责「谁和谁有关系」，关系型/列式表负责「那笔钱具体怎么回事」，
两边用交易 ID 关联。

**本期不采用的原因**：增加了一层数据一致性负担（图与表要同步），
而本项目的核心价值在**检测方法与评测**，不在工程复杂度。**记录为后续演进方向。**

---

## 后果

### 正面

- 环路检测、社区发现的查询**最直接**，性能好；
- 图规模落在既定规格内；
- 交易属性作为边的属性，Cypher 里可直接用于过滤与加权。

### 负面（**必须知道，面试会问**）

- **边只能连接两个端点**——无法把「设备」「IP」挂到某一笔**具体交易**上；
- 「一进多出」只能表达为多条边，**不能作为一件事**聚合；
- 边属性一旦写入，**更新语义较弱**（交易一般不可变，所以影响小）。

### 缓解

- 若未来需要设备/IP 关联，**只对可疑子图做「交易升格」**（把该子图的交易转为节点），
  而不是全图改造——**局部代价换局部能力**。

---

## 什么情况下需要重新审视这个决策

| 触发条件 | 说明 |
|---|---|
| 需求扩展到**设备/IP 关联分析** | 反欺诈场景的典型需求 |
| 需要把**一进多出**作为单一事件建模 | 如「集中转入、分散转出」的团伙识别 |
| 出现**监管审计**的双时间轴要求 | 金融行业合规常见 |
| 图规模逼近单机上限 | 需要重新评估分片策略 |

**只要出现其中任意一条，本 ADR 就应被重新打开讨论。**

---

## 附：这个决策的面试讲法

> 「转账是边还是节点，是图建模的第一个岔路口。
>
> 我选了**边**，理由不是规模小——**是因为我要回答的核心问题是"资金回流环路"，那是个路径问题**。
> 交易是边，路径就是边序列，查环路最直接。
>
> 我也知道**放弃了什么**：边只能连两个端点，所以**没法把设备、IP 挂到某笔具体交易上**，
> 也没法把"一进多出"当成一件事来聚合。
>
> 但这两项**都在我的范围之外**——设备/IP 是反欺诈的问题域，我明确不做；
> 而真实系统里更常见的做法是**图存结构、关系表存明细**，我把它记成了后续演进方向。
>
> **这个取舍我记录在 ADR 里，触发条件也写明了。**」

# ADR-0002：本期不做「担保 / 持股 / 任职」关系，模式 P5 / P6 推迟

## 状态

**已接受**（2026-XX-XX）

---

## 背景

在设计图谱 schema 时，列了六类待检测的可疑模式：

| 编号 | 可疑模式 | 需要的关系 |
|---|---|---|
| P1 | 回流环路 | 转账 |
| P2 | 拆分 / 分层 | 转账 |
| P3 | 集中转入、分散转出 | 转账 |
| P4 | 同一实体的多个账户互转 | 转账 + **实体–账户** |
| **P5** | **关联企业互保圈** | **担保 + 持股** |
| **P6** | **隐形关联（同法人）** | **任职 + 持股** |

需求方（也就是我们自己）最初的选择是「**六个全要**」。

---

## 决策

**本期只做 P1–P4。P5、P6 推迟，记为演进方向。**

---

## 理由

### 1. 数据不支持（**决定性理由**）

主数据集是 IBM 的合成反洗钱交易数据。它包含：

| 内容 | 有吗 |
|---|---|
| 交易流水（含「是否洗钱」标签） | ✅ |
| 账户 → 所属银行 / **所属实体** | ✅ |
| **已发表分类法**的注入模式清单（CYCLE / FAN-IN / FAN-OUT / STACK …） | ✅ |
| **公司持股关系** | ❌ |
| **公司间担保关系** | ❌ |
| **高管任职 / 法人关系** | ❌ |

**P5 和 P6 需要的是「工商数据」——主数据集里根本没有。**

### 2. 补数据源的代价被低估了

补一份公开工商数据听起来只是「多接一个源」，实际上卡在一个**独立的大问题**上：

> **实体对齐（Entity Resolution）**——你怎么知道工商数据里的「张三」
> 和交易数据里的「张三」是同一个人？

**实体对齐本身就是 AML 领域的一个专门课题**，有独立的算法和评测。
把它塞进这个项目，会**把项目拖进一个不属于它的坑**，而且大概率做不完。

### 3. 剩下的四个模式已经够强

**P1–P3 是这个行业最主流的检测目标**（对应数据集自带的 CYCLE / FAN / STACK 分类）。
**把它做深，比铺开六个模式更有说服力。**

### 4. 「知道有 P5/P6，也知道为什么不做」本身就是深度

面试时说清楚这个取舍，**比硬做一半强得多**。

---

## 考虑过的替代方案

| 方案 | 做法 | 放弃原因 |
|---|---|---|
| **补公开工商数据源** | 再接一份股权/担保数据，与主图做实体对齐 | **实体对齐是独立大课题**，工作量翻倍且大概率做不完 |
| **合成这部分关系** | 自己造持股/担保边 | 数据是假的，**面试官一问"这数据哪来的"就崩**；且合成的结构不具备真实统计特性 |

---

## 后果

### 正面

- 范围收敛，可以把 P1–P4 做深；
- 图规模落在既定规格内（不留 P5/P6 的实体空间）。

### 负面（**必须知道**）

- **无法检测「互保圈」「隐形关联」这两类真实存在的重要模式**；
- 「同一控制人」的判定**弱化为「同一实体名」**——因为数据里没有自然人标识。
  这是一个**已知的、被接受的**精度损失。

---

## 什么情况下需要重新审视这个决策

| 触发条件 | 说明 |
|---|---|
| 拿到真实的工商/股权数据源 | 数据问题解决，P5/P6 即可解锁 |
| 项目目标从「验证方法」转向「覆盖更多模式」 | 优先级变化 |
| 实体对齐有现成的可信方案可用 | 主要成本消失 |

---

## 附：这个决策的面试讲法

> 「我列了六类可疑模式，最初想全做。但一做数据现实检查就发现：
> **P1–P3 用转账关系就够，P4 勉强够，而 P5『互保圈』和 P6『隐形关联』需要持股、担保、任职关系——
> 主数据集里根本没有这些。**
>
> 补一份工商数据听起来简单，但它卡在**实体对齐**上：你怎么知道工商数据里的『张三』和交易数据里的『张三』是同一个人？
> **那本身就是 AML 领域的一个专门课题**，塞进来会把项目拖进一个不属于它的坑。
>
> 所以我砍掉了 P5/P6，但**把触发条件写进了 ADR**——
> 一旦有可信的工商数据源和实体对齐方案，这两个模式就能解锁。
>
> **我的判断是：把 P1–P4 做深，比铺开六个模式更有说服力。**」

> ⚠️ **本 ADR 已被 ADR-0004 部分修正**：实测数据显示原生数据**只支持 P1 和 P3(扇入)**，
> 且客户:账户为 1:1，**P4 无数据支撑**。请一并阅读 ADR-0004。

---

# ADR-0004：数据源改为 AMLSim 示例集，并据此修正三处需求

## 状态

**已接受**（2026-XX-XX）

---

## 背景

PRD 与 ADR-0002 都建立在「使用 Kaggle 上的 IBM Transactions for AML 完整数据集」之上。

M1（数据与真值准备）做可行性验证时发现：

> **该数据集打包为 41.6 GB**（HI-Small / HI-Medium / HI-Large 合在一个 archive 里），
> **不可行**——磁盘、带宽、时间成本都不划算。

**这正是 M1 存在的意义。** 若按原计划推进，该问题会在 M3 才暴露。

---

## 决策

**改用 IBM AMLSim Example Dataset**（Kaggle `anshankul/ibm-amlsim-example-dataset`，
压缩 11.9 MB / 解压 61.5 MB，Apache 2.0），并**据此修正三处需求**。

同时确定真值方案为 **「原生 + 注入」**：

| 来源 | 模式 |
|---|---|
| **原生**（数据集自带标注） | `cycle`（936）、`fan_in`（783） |
| **受控注入**（真值即注入位置） | `stack`（分层）、`fan_out`（扇出）、**同控制人多账户**、**结构相似负例** |

---

## 理由

### 1. AMLSim 与我们的设计高度吻合

数据集官方描述：**「生成合成银行交易数据，以及一组已知的洗钱模式——
主要用于测试机器学习模型和图算法」**。

| AMLSim 提供 | 对应我们的设计 |
|---|---|
| `ACCOUNT_ID` | `Account` 节点 |
| `CUSTOMER_ID` | `Entity` 节点 |
| `SENDER` → `RECEIVER` | **`TRANSFER` 边（正是 ADR-0001 的建模）** |
| `TX_AMOUNT` / `TIMESTAMP` | 边属性 |
| `ALERT_TYPE` | 已知模式分类 |

### 2. 规模反而更好

| | 原定 NFR-2 | AMLSim 实测 |
|---|---|---|
| 边 | ≥ 100 万 | **132 万** ✅ **超过** |
| 节点 | ≥ 10 万 | 1 万 ❌ |

**边数是图遍历的主要成本**，而它超了目标；节点数偏低但图密度高（入度最大 4,843）。

### 3. 「原生 + 注入」兼顾真实性与广度

- **原生部分保证真实性**——`cycle`/`fan_in` 是数据集官方标注，不是我们造的；
- **注入部分保证广度**——真值即注入位置，**与产线项目的故障注入是同一套方法**；
- 两个项目方法一致，面试时可讲成连贯的方法论。

---

## 三处需求修正（**本 ADR 最重要的部分**）

| # | 原需求 | 修正为 | 修正依据 |
|---|---|---|---|
| **R1** | NFR-2 规模：**10 万节点 / 100 万边** | **1 万节点 / 132 万边** | 数据实测 |
| **R2** | 原生支持 P1–P4 四类模式 | **P1 与 P3(扇入) 原生；P2 / 扇出 / P4 靠注入** | 原生只有 `cycle`/`fan_in`；且客户:账户 = 1:1，**P4 无数据支撑** |
| **R3** | 时序模式：**快进快出**检测 | **降级为粗粒度分层时序** | `TIMESTAMP` 只有 200 个离散刻度 |

**同时更正一处错误判断**：

> 先前认为 `alerts.csv` 可作为「规则基线」直接对比。
> **实测：1,719 条告警的 `IS_FRAUD` 全部为 `True`**——
> 它是**零误报的真值清单**，不是带噪声的规则引擎输出。
> **规则基线必须我们自己实现。**

---

## 考虑过的替代方案

| 方案 | 放弃原因 |
|---|---|
| 硬扛 41.6 GB 原数据集 | 磁盘/带宽/时间都不划算 |
| 用 Elliptic 比特币数据集 | **节点=交易而非账户**，与 ADR-0001 冲突；且许可为 ND（禁止演绎） |
| 用 IBM AML Stateful（610 MB） | 特征已预先算好，**图的用武之地变小** |
| 用 SAML-D（996 MB） | 是表格数据不是图 |
| 用 AMLSim 生成器自造更大数据 | **生成器在 GitHub 上，本机 github.com 不通；PyPI 上也无包** |

---

## 后果

### 正面

- 数据获取**无需账号**（Kaggle 下载接口 302 重定向到签名 URL）；
- **132 万条边**，图结构密集，算法有发挥空间；
- 有**原生真值**，评测的可靠性有保障；
- 数据集小，**全流程可在本机跑完**（符合零 API 成本约束）。

### 负面（**必须知道**）

- **节点数只有 1 万**，「十万节点」的规模论证不再成立——**但百万边的论证仍然成立**；
- **属性维度贫瘠**：`COUNTRY`、`ACCOUNT_TYPE` 均只有 1 种值，无法用作特征；
- **时间粒度粗**（200 刻度），时序类模式做不细；
- **注入的模式是合成的**——面试时**必须主动说明**（主动说明比被问出来强）。

### 数据质量问题（已记录在 `08-数据规格` 第 4 节）

- 3,053 笔金额为 `2³¹/100`，疑似哨兵值；
- 19 笔金额为 0；
- 181 笔自环，环路检测需显式排除。

---

## 什么情况下需要重新审视这个决策

| 触发条件 | 说明 |
|---|---|
| 需要「十万节点」级规模 | 需解决 AMLSim 生成器的获取问题（网络或镜像） |
| 需要细粒度时序模式 | 需换数据源或自行加密时间刻度 |
| 需要更丰富的属性维度 | 需融合外部数据源 |
| 找到更丰富的图数据集 | 重新评估数据源 |

---

## 附：这个决策的面试讲法

> 「我在数据准备阶段发现一个问题：**原定的数据集打包是 41.6 GB，不可行。**
> 如果按原计划往下做，这个问题要到开发中期才暴露。
>
> 我换成了 IBM 的 **AMLSim**——它官方定位就是『**为测试图算法而生成合成银行交易数据**』，
> 而且**边数 132 万，反而超过了我原定的百万边目标**。
>
> 但换数据**推翻了三个设计假设**：节点数从十万降到一万、
> 原生只支持两种模式、时间粒度不够做时序检测。
>
> **我把这三处修正全部写进了 ADR**，包括修正依据和触发重新审视的条件。
>
> 我的原则是：**被数据推翻需求是常态，关键是把变更记录下来，而不是改数据去迁就需求。**」
