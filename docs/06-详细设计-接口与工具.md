# 06 · 详细设计（二）：接口与工具契约

> 回答「Agent 到底能做什么、不能做什么」。
>
> **面试被问「Agent 的工具有哪些、怎么定义」——翻这一页。**
>
> 这份文档的每一条**参数上界都对应一条非功能需求**，不是随手定的。

---

## 1. 通用约定

### 1.1 为什么是「受控工具」而不是「自由生成 Cypher」

| 理由 | 说明 | 对应需求 |
|---|---|---|
| **不可控** | LLM 可能生成全图扫描，直接打破响应时间 | NFR-1 |
| **不确定** | 同问题生成不同查询，无法复现 | NFR-5 |
| **不可审** | 生成的查询无法预先审计，**而这是金融系统** | — |

**结论**：Agent **只能**调用本文件定义的 4 个工具，
**参数上界由服务端强制校验**（不是靠提示词约束）。

### 1.2 三条通用铁律

| 铁律 | 说明 |
|---|---|
| **参数越界必须报错，不能静默截断** | 静默截断会让 Agent 以为拿到了完整结果 |
| **「没查到」和「查失败」必须区分** | 前者是合法结果，后者是异常——**Agent 的后续决策完全不同** |
| **所有工具幂等** | 同一参数重复调用结果一致（NFR-5） |

---

## 2. 工具一：`investigate`（侦查）

```python
investigate(account_key: str, hops: int = 2) -> InvestigationReport
```

### 输入

| 参数 | 类型 | 约束 | 为什么这么约束 |
|---|---|---|---|
| `account_key` | string | 格式 `{bank}:{account_number}` | 见 `04-详细设计` 3.1（防跨行同名合并） |
| `hops` | int | **1 ≤ hops ≤ 3** | ⚠️ **邻域规模随跳数指数增长**——hops=4 时节点数可能爆炸，**直接打破 30 秒约束** |

### 输出（`InvestigationReport`）

```json
{
  "account": "BANK_A:1234567",
  "neighborhood": {
    "nodes": 128, "edges": 341, "hops": 2,
    "timeSpan": {"from": "...", "to": "..."}
  },
  "cycleCandidates": [
    {
      "accounts": ["BANK_A:1234567", "BANK_B:8888", "BANK_A:1234567"],
      "length": 3, "totalAmount": 4700000, "score": 0.86,
      "evidenceTransactionIds": ["T-1001", "T-1002", "T-1003"]
    }
  ],
  "communityDensity": 0.72,
  "hubRanking": [{"account": "...", "centrality": 0.91}],
  "truncated": false
}
```

**关键字段说明：**

| 字段 | 为什么存在 |
|---|---|
| `evidenceTransactionIds` | **证据回链的入口**（NFR-3）——结论必须能挂到具体交易 |
| `score` | **可排序分数**（FR-9）——两个主指标的基础 |
| `truncated` | ⚠️ **是否被截断**。若为 `true`，Agent 必须知道结果不完整，**不能当成"只有这些"** |

### 错误

| 情况 | 返回 |
|---|---|
| 账户不存在 | `ACCOUNT_NOT_FOUND`（**不是空报告**） |
| `hops` 越界 | `INVALID_ARGUMENT: hops must be 1..3` |

## 3. 工具二：`match_patterns`（手法匹配）

```python
match_patterns(structure: str, top_k: int = 3) -> list[PatternMatch]
```

### 输入

| 参数 | 类型 | 约束 |
|---|---|---|
| `structure` | string | 结构特征的**文字描述**（由系统生成，不是 Agent 自由编） |
| `top_k` | int | **1 ≤ top_k ≤ 5** |

### 输出

```json
[
  {
    "patternId": "CYCLE",
    "name": "分层回流",
    "similarity": 0.81,
    "description": "（模式库原文，非 LLM 生成）",
    "source": "数据集自带分类法 / 公开文献"
  }
]
```

⚠️ **`description` 必须是模式库原文。** 不许 LLM 改写或生成——
因为它是**要写进上报材料的解释**，必须可追溯。

### 与 ADR-0003 的关系

本工具是 GraphRAG 里**向量的那一半**。它回答的是：

> 图告诉你有异常结构，**但告诉不了你这叫什么、意味着什么**。

## 4. 工具三：`get_transactions`（证据查询）

```python
get_transactions(
    from_account: str,
    to_account: str | None = None,
    start: datetime | None = None,
    end: datetime | None = None,
    limit: int = 100,
) -> TransactionPage
```

| 参数 | 约束 | 为什么 |
|---|---|---|
| `to_account` | 可选 | 不传则返回该账户的**全部**进出流水 |
| `limit` | **1 ≤ limit ≤ 500** | 保护上下文长度与响应时间 |
| 时间范围 | 可选 | 时序模式分析需要 |

**输出**：交易列表，每条含 `transactionId`、金额、时间、方向。

⚠️ **输出中不得包含 `is_laundering` 字段。**

> 这是**标签泄漏**的防线（NFR-6）。哪怕上游数据里有，
> **这一层的输出必须剥掉**——而且要有自动化测试守着。

### 这是硬约束 C 的兑现点

> 任何结论都必须能通过本工具**追溯到具体交易**。
> 做不到的结论，**在合规场景下等于零价值**。

## 5. 工具四：`trace_path`（路径查询）

```python
trace_path(from_account: str, to_account: str, max_length: int = 8) -> PathResult
```

| 参数 | 约束 | 为什么 |
|---|---|---|
| `max_length` | **1 ≤ max_length ≤ 8** | ⚠️ **找所有环是组合爆炸问题**，长度上界是**必须的工程约束**，不是保守 |

**输出**：

```json
{
  "found": true,
  "paths": [{"accounts": [...], "totalAmount": 4700000,
             "evidenceTransactionIds": [...]}],
  "truncated": false
}
```

⚠️ **必须区分三种情况**：

| 情况 | 返回 |
|---|---|
| 有路径 | `found: true` + paths |
| **确认无路径** | `found: false`, `paths: []` |
| 查了但被截断 | `found: true`, `truncated: true` |

> **「确认没有」和「没查到」不是一回事。**
> 混在一起会让 Agent 做出错误判断——比如把「路径太长没找完」当成「没有关联」。

---

## 6. 工具描述怎么写（**这本身是 Agent 设计的一部分**）

工具描述直接影响 Agent 会不会正确使用它。我们的约定：

| 约定 | 例子 |
|---|---|
| **说清"什么时候用"** | ✅「当你需要判断两个主体是否有关联时用」<br>❌「查询路径」 |
| **说清"代价"** | ✅「hops 越大越慢，默认 2」 |
| **说清"边界"** | ✅「最多 3 跳，超过请分次调用」 |
| **不要诱导** | ❌ 不要在描述里写"通常能找到洗钱证据"——那会让 Agent 过度报告 |

**最后一条特别重要**：工具描述**会显著影响 Agent 的倾向**。
写得太"鼓励"，Agent 就会什么都报（误报率上升）；
写得太"劝退"，Agent 就什么都不报（漏报率上升）。

> **这是提示工程的一部分，而且是可测量的**——我们的 A/B 评测就能看出不同描述的影响。

---

## 7. 工具清单（总览）

| 层 | 工具 | 参数上界 | 保护哪条需求 |
|---|---|---|---|
| 侦查 | `investigate` | `hops ≤ 3` | NFR-1 响应时间 |
| 验证 | `match_patterns` | `top_k ≤ 5` | NFR-1 |
| 验证 | `get_transactions` | `limit ≤ 500` | NFR-1 / NFR-6 标签隔离 |
| 验证 | `trace_path` | `max_length ≤ 8` | NFR-1（组合爆炸） |

**共 4 个。** 每多一个就多一份"选错"的概率（HLD 7.2）。

---

## 8. 面试讲法

> 「工具设计我做了三件事。
>
> **第一，不让 Agent 自由生成 Cypher，只给 4 个受控工具**——因为自由生成的查询可能全图扫描，
> 直接打破我的响应时间约束；而且同一问题可能生成不同查询，**违反可复现**。
>
> **第二，每个参数上界都对应一条非功能需求。**
> 比如 `hops ≤ 3` 是因为邻域随跳数指数增长；`max_length ≤ 8` 是因为找所有环是组合爆炸。
> **上界不是保守，是必须的工程约束。**
>
> **第三，我严格区分「确认没有」和「没查到」，还加了 `truncated` 字段**——
> 混在一起会让 Agent 把『路径太长没找完』误判成『两者没有关联』。
>
> 另外**工具的描述文字也是设计的一部分**：写得鼓励一点 Agent 就滥报，
> 写得劝退一点就漏报——**而这个影响是可测量的，正好用我的 A/B 评测验证。**」
