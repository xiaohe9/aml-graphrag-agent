# 04 · 详细设计（一）：图谱建模

> 这是**图项目的核心设计文档**。面试时被问「图怎么建的」，答案全在这里。

---

## 1. Schema 总览

```text
        ┌──────────────────────────────────────────┐
        │              Entity（实体/机构）           │
        │              key: name                    │
        └──────────────────┬───────────────────────┘
                           │ CONTROLS（所属）
                           │
        ┌──────────────────▼───────────────────────┐
        │              Account（账户）              │
        │   key: (bank, account_number)  ⚠️ 见 3.1  │
        │   props: bank, entity, ...               │
        └──────────────────┬───────────────────────┘
                           │
                      TRANSFER（转账）
                           │  amount / timestamp / currency
                           │  payment_format / is_laundering
                           ▼
        ┌──────────────────────────────────────────┐
        │              Account（账户）              │
        └──────────────────────────────────────────┘
```

---

## 2. 节点定义

### 2.1 `Account`（账户）

| 属性 | 类型 | 说明 |
|---|---|---|
| `bank` | string | 所属银行 |
| `account_number` | string | 账号 |
| `key` | string | **唯一键 = `{bank}:{account_number}`**（见 3.1） |
| `entity` | string | 所属实体名（**冗余存储**，见 3.2） |

### 2.2 `Entity`（实体 / 机构）

| 属性 | 类型 | 说明 |
|---|---|---|
| `name` | string | 实体名（唯一） |

**注意**：数据集里的「Entity」是**机构名，不是自然人**。
所以「同一控制人」在本项目里**弱化为「同一实体名」**——这是**已知且被接受的精度损失**
（原因见 `05-ADR-决策记录.md` ADR-0002）。

## 3. 三个关键设计点（面试会追问）

### 3.1 ⚠️ 账户主键：**设计原则保留，但本数据集不体现**（M1 数据核查后已更正）

**原本的设计理由**（这个理由本身是对的，但它来自**另一个数据集**）：

> 「账号在不同银行之间会重复。只用账号做主键，会把两家银行的同名账号合并成同一个节点，
> 图上凭空多出不存在的资金路径，**直接制造假阳性**。」

**M1 实测后更正**：

> **AMLSim 数据集里没有「银行」这一维**，`ACCOUNT_ID` 是全局唯一的整数，**不存在跨行重名**。

**错误来源**：我把**两个数据集搞混了**——那个 41.6 GB 的 IBM 完整集**有** `From Bank` / `To Bank` 列，
AMLSim **没有**。（同类错误还有一次：把 `alerts.csv` 误判成「规则基线」，实际它全部 `IS_FRAUD=True`。）
**共同原因：我读了数据集描述就下结论，没有先核对实际字段。**

**最终决定**：

| 项 | 决定 |
|---|---|
| 本项目主键 | **`Account.key = str(ACCOUNT_ID)`** |
| 键的类型 | ⚠️ **字符串，不是整数**——这是刻意的，见下 |
| 设计原则 | **保留在文档里**（跨机构部署时必须把机构编进键） |

**为什么仍然把键设计成字符串**：

> 一旦接入**跨机构**数据（真实场景必然如此），键就要扩成 `{机构}:{账号}`。
> **用一个不透明的字符串做键，这个扩展不需要改数据库 schema，也不需要改任何下游代码。**
>
> **所以原则以另一种形式活了下来：主键的构成要能容纳未来的维度。**

**这个原则在真实系统里是对的**——洗钱最常见的手法之一就是**跨行转账**。
本数据集是封闭模拟，恰好没有这一维，**但设计不能因此退化**。

### 3.2 ⚠️ 「所属实体」为什么**既做属性、又做关系**？

同一个信息，在图里可以有两种建模方式。**选哪个取决于「你要不要在图查询里用它」**：

| 建模方式 | 能回答 | 查不了 |
|---|---|---|
| **属性** `Account.entity` | 「这个账户属于谁」（单点查询，快） | 「**经过同一实体的资金路径**」 |
| **关系** `(Entity)-[:CONTROLS]->(Account)` | 「同一实体的所有账户」+ **能在路径查询里用** | 稍慢 |

**我们两个都要**，理由：

- **属性**用于过滤和展示（分析师要看"这个账户属于谁"）；
- **关系**用于**路径查询**——模式 P4「同一实体的多个账户互转」，
  在图上是 `账户A ←CONTROLS— Entity —CONTROLS→ 账户B`，**没有这条边就问不出来**。

> **这条经验可以迁移**：**同一个事实，做属性还是做关系，取决于它要不要参与路径查询。**
> 做错了，要么查不出来，要么图白白变大。

### 3.3 ⚠️ 同一对账户之间的多笔转账，为什么不聚合成一条边？

数据里同一对账户之间会有**很多笔**转账。有两种建法：

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **聚合** | `A → B` 合成一条边，记总额和笔数 | 图**小很多** | **丢失时间信息** |
| **不聚合**（我们选的） | 一笔转账 = 一条边 | **保留时间戳**，可查时序模式 | 边数 = 交易笔数（**百万级**） |

**选不聚合的理由**：可疑模式里有**时序特征**——

- 「**快进快出**」：钱进来几小时内就转走；
- 「**分层**」：固定时间间隔的连续小额转账。

**聚合成一条边，这两类模式就检测不了了。**

**代价是边数达到百万级**——而这正是我们非功能需求里定的规模（百万级边）。
**所以规模不是拍脑袋定的，是被建模决策推出来的。**

## 4. 关系定义

### 4.1 `TRANSFER`（转账）

| 属性 | 类型 | 说明 |
|---|---|---|
| `amount` | float | 金额 |
| `timestamp` | int | 交易时间（**必须保留，见 3.3**） |
| `txId` | int | 交易 ID（评测的 join key） |
| `isSentinelAmount` | bool | 疑似溢出金额的标记（**派生，不是标签**，见 `docs/08` Q1） |

### ⚠️ 4.1.1 标签**不写进图**（M3 后的设计变更）

**原本**这里写的是「`is_laundering` 存在边上，仅供评测，绝不可作为特征」。

**实测发现问题**：只要标签在图上，**任何 `RETURN t` 都会把它带出来**。
实测确认过：

```text
图上 TRANSFER 属性：['isSentinelAmount', 'txId', 'timestamp', 'amount', 'isFraud']
一条普通查询就能按标签筛选 —— 等于把答案交给 Agent。
```

**改成：标签根本不写进图。**

> **图是特征存储，不是答案存储。**
> 评测需要标签时**从 CSV 读**（`data/loader.py`），不经过图。

**理由**：**最强的访问控制，是不把秘密放在那里。**
白名单和自动检查都是第二、第三层——**如果秘密不在那里，前两层根本不需要生效**。

**三层防御**（详见 `src/aml_agent/graph/guard.py` 的模块文档）：

| 层 | 实现 | 强度 |
|---|---|---|
| **① 不存** | `cypher.IMPORT_TRANSFERS` 里没有标签；建图后自动核对属性清单 | **最强** |
| **② 白名单** | `queries.py` 的 `RETURN` 子句**从白名单生成**，写不错 | 强 |
| **③ 自动审计** | `guard.collect_queries()` 扫描代码库里**全部**查询，逐条过检查 | 兜底 |

**第 ③ 层有个设计要点**：它**自动发现**查询（扫大写字符串常量），
而**不是维护一份手写清单**——**手写清单会漏掉新增的查询，而漏掉的那条就是漏洞。**

### 4.2 `CONTROLS`（所属）

`(Entity)-[:CONTROLS]->(Account)`，无属性。

## 5. 索引设计（Neo4j）

| 索引 | 类型 | 用途 |
|---|---|---|
| `Account.key` | 唯一索引 | 高效定位账户 |
| `Entity.name` | 唯一索引 | 高效定位实体 |
| `Account.bank` | 普通索引 | 按银行过滤 |
| `TRANSFER.timestamp` | 关系属性索引 | **时间范围查询**（时序模式必需） |

**为什么 `timestamp` 要建索引**：时序模式（快进快出、固定间隔）都是**时间范围查询**，
没有索引会全图扫描，**直接打破 30 秒响应的约束**。

## 6. 规模估算（目标值，M1 数据到手后确认）

| 对象 | 目标量级 | 依据 |
|---|---|---|
| `Account` | 十万级 | 数据集的账户数 |
| `Entity` | 千级～万级 | 账户的所属机构数，远少于账户 |
| `TRANSFER` | **百万级** | 交易笔数（**因为不聚合，见 3.3**） |
| `CONTROLS` | 十万级 | 每个账户一条 |

**节点 ~10 万、边 ~100 万** —— 正好落在非功能需求定的规格内。

## 7. 覆盖的可疑模式 vs 图谱元素

| 模式 | 用到的图元素 | 数据支持 |
|---|---|---|
| P1 回流环路 | `TRANSFER` | ✅ |
| P2 拆分 / 分层 | `TRANSFER` + `timestamp` | ✅ |
| P3 集中转入 / 分散转出 | `TRANSFER` | ✅ |
| P4 同一实体多账户互转 | `TRANSFER` + `CONTROLS` | ⚠️ 弱化为「同一实体名」 |
| ~~P5 互保圈~~ | ~~担保 + 持股~~ | ❌ 见 ADR-0002 |
| ~~P6 隐形关联~~ | ~~任职 + 持股~~ | ❌ 见 ADR-0002 |

## 8. 面试讲法（浓缩版）

> 「图建模我做了三个关键决定。
>
> **第一，账户主键用『银行 + 账号』，不是只用账号**——因为账号在不同银行会重复，
> 只用账号会把两个不同银行的同名账号合并，**凭空造出不存在的资金路径，直接制造假阳性**。
>
> **第二，『所属实体』我既做了属性、又做了关系**。属性用于展示，
> 关系用于**路径查询**——模式『同一实体的多个账户互转』必须靠这条边才问得出来。
> **同一个事实做属性还是做关系，取决于它要不要参与路径查询。**
>
> **第三，同一对账户之间的多笔转账我不聚合**。因为可疑模式里有**时序特征**，
> 比如『快进快出』和固定间隔的分层转账——聚合了时间就丢了，这两类就检测不了。
> 代价是边数到百万级，**而这就是我的规模指标是被建模决策推出来的，不是拍脑袋定的。**」
