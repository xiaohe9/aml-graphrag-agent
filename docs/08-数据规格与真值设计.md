## 1. 数据源

| 项 | 内容 |
|---|---|
| 名称 | **IBM AMLSim Example Dataset** |
| 来源 | Kaggle `anshankul/ibm-amlsim-example-dataset` |
| 原始项目 | IBM **AMLSim** —— 多智能体银行交易模拟器，**专门为「测试机器学习模型和图算法」而设计** |
| 许可 | **Apache 2.0**（宽松，可留档） |
| 大小 | 压缩 11.9 MB / 解压 61.5 MB |
| 获取方式 | **无需账号**——Kaggle 下载接口 302 重定向到签名 URL |

### 1.1 为什么换掉了原定数据集（**这是 M1 最重要的发现**）

原计划使用 Kaggle 上的 **IBM Transactions for AML** 完整集。实测发现：

> **该数据集打包为 41.6 GB**（HI-Small / HI-Medium / HI-Large 三档合在一个 archive 里），
> **不可行**（磁盘、带宽、时间）。

**这是 M1 存在的意义**——如果按原计划往下做，这个问题会在 M3 才暴露，代价大得多。

**详见 `05-ADR-决策记录.md` ADR-0004。**

## 2. 三张表

### 2.1 `accounts.csv`（10,000 行）

| 字段 | 类型 | 含义 | **可用性** |
|---|---|---|---|
| `ACCOUNT_ID` | int | 账户 ID | ✅ 主键 |
| `CUSTOMER_ID` | string | 客户 ID（`C_0` … `C_9999`） | ✅ **即设计中的 `Entity`** |
| `INIT_BALANCE` | float | 初始余额 | ✅ |
| `COUNTRY` | string | 国别 | ❌ **只有 1 种值（US）** |
| `ACCOUNT_TYPE` | string | 账户类型 | ❌ **只有 1 种值（I）** |
| `IS_FRAUD` | bool | ⚠️ **是否涉诈（标签）** | ⚠️ **禁止进模型输入** |
| `TX_BEHAVIOR_ID` | int | 行为分组（1–5，每组恰好 2000 账户） | ⚠️ 见下方说明 |

**关于 `TX_BEHAVIOR_ID`**：我一度以为它藏着更多模式类型。实测**不是**——
五组的涉诈占比分别为 14.6% / 16.5% / 15.4% / 17.9% / 19.8%，
**每组恰好 2000 个账户**，是**随机分组**，不承载模式语义。

### 2.2 `transactions.csv`（1,323,234 行）

| 字段 | 类型 | 含义 |
|---|---|---|
| `TX_ID` | int | 交易 ID |
| `SENDER_ACCOUNT_ID` | int | **转出账户 → 边起点** |
| `RECEIVER_ACCOUNT_ID` | int | **转入账户 → 边终点** |
| `TX_TYPE` | string | 交易类型（**全部为 `TRANSFER`**） |
| `TX_AMOUNT` | float | 金额 |
| `TIMESTAMP` | int | 时间（**离散刻度 0–199**） |
| `IS_FRAUD` | bool | ⚠️ **标签** |
| `ALERT_ID` | int | 关联告警（`-1` 表示无） |

**这张表就是我们的 `TRANSFER` 边集合**——`(SENDER)-[:TRANSFER]->(RECEIVER)`，
完全对应 ADR-0001 的建模决策。

### 2.3 `alerts.csv`（1,719 行）

| 字段 | 含义 |
|---|---|
| `ALERT_ID`, `ALERT_TYPE`, `TX_ID`, `SENDER_ACCOUNT_ID`, `RECEIVER_ACCOUNT_ID`, `TX_TYPE`, `TX_AMOUNT`, `TIMESTAMP` | 告警明细 |
| `ALERT_TYPE` | **模式类型：`cycle`（936）/ `fan_in`（783）** |
| `IS_FRAUD` | ⚠️ **全部为 `True`** |

### ⚠️ 2.4 更正：`alerts.csv` **不是**「规则基线」

我先前判断「alerts 就是规则引擎的告警，可直接作为基线对比」——**这是错的**。

> **实测：1,719 条告警的 `IS_FRAUD` 全部为 `True`。**
>
> 也就是说，它是一个**零误报的完美系统**的输出，**不是**带噪声的规则引擎告警。

**对评测的影响**：

- ❌ **不能**把它当作「有误报的规则基线」；
- ✅ 它是**精确的真值清单**（可用于核对我们的检测）；
- ⚠️ **规则基线必须我们自己实现**。

## 3. 数据画像（实测）

### 3.1 规模

| 项 | 实测 | 原定 NFR-2 | 判定 |
|---|---|---|---|
| 账户节点 | **10,000** | ≥ 100,000 | ❌ 差 10 倍 |
| 客户节点 | 10,000（**与账户 1:1**） | — | ⚠️ 见 4.3 |
| **交易边** | **1,323,234** | ≥ 1,000,000 | ✅ **超过目标** |
| 涉诈交易 | 1,719（**0.13%**） | — | 极度不平衡 |

### 3.2 图结构

| 指标 | 值 |
|---|---|
| 出度 中位数 / 最大 | 132 / 963 |
| 入度 中位数 / 最大 | 80 / **4,843** |
| 参与交易的账户 | 9,999 / 10,000 |
| **自环**（自己转自己） | **181 笔** |

**这是一个真有结构的图**（入度最大 4,843 说明存在超级枢纽），不是稀疏散点。
**这决定了图算法有发挥空间。**

### 3.3 🎯 关键发现：**涉诈交易的金额极小**

| 金额分位 | 正常交易 | **涉诈交易** |
|---|---|---|
| 中位数 | 156.71 | **10.60** |
| 99 分位 | 1,854,724.69 | **19.54** |

> **洗钱交易的金额中位数只有正常交易的 1/15 左右。**

**这是 PRD 核心论断的实测证据**：

> 如果实现一个「单笔金额超阈值就报警」的规则基线，
> **它的检出率是 —— 0%。一笔都抓不到。**

**面试时的说法**：

> 「我在真实数据上验证过——**单笔金额规则对洗钱交易的检出率是 0%**，
> 因为洗钱金额的中位数只有正常交易的 1/15。
> **这不是我的假设，是我测出来的。**」

## 4. 数据质量问题与处理方案

| # | 问题 | 影响 | 处理方案 | 状态 |
|---|---|---|---|---|
| Q1 | **3,053 笔金额 = `21474836.47`（= 2³¹/100）** | 明显是哨兵/溢出值，会污染金额统计 | 标记为**哨兵值**；统计时排除，**原值保留**（不篡改原始数据） | 待处理 |
| Q2 | 19 笔金额 = 0 | 语义不明的零额转账 | 保留，但**在聚合统计中单独说明** | 待处理 |
| Q3 | `COUNTRY` / `ACCOUNT_TYPE` 只有 1 种值 | 无法作为过滤/特征维度 | **不使用**；这也说明数据集是"简化模拟" | 已决定 |
| Q4 | 时间只有 200 个离散刻度 | 时序模式（快进快出）**做不细** | **降级**：只做"跨刻度的分层"类粗粒度时序，不做"小时级快进快出" | 已决定 |
| Q5 | 181 笔自环 | 环路检测可能把自环当成长度 1 的环 | 检测时**显式排除自环**（或单独报告） | 待处理 |
| Q6 | 客户:账户 = 1:1 | **P4「同一控制人多账户」无数据支撑** | 见 5.2 的注入方案 | 待处理 |
| **Q7** | **⚠️ 没有任何「银行 / 机构」维度** | **ADR-0001 里「账号跨行会重复」的设计前提在本数据集不成立** | 主键用 `str(ACCOUNT_ID)`，但**保持字符串类型**，以便将来扩成 `{机构}:{账号}`；设计原则保留在 `04-详细设计` 3.1 | 已决定 |

### 4.1 关于 Q7：一次把数据集搞混的错误

我在设计阶段写下「账户主键用 `(银行, 账号)`，因为账号在不同银行之间会重复」——
**这个理由本身是对的，但它来自另一个数据集**：

| 数据集 | 有银行维度吗 |
|---|---|
| IBM AML 完整集（41.6 GB，**未采用**） | ✅ 有 `From Bank` / `To Bank` |
| **AMLSim（实际采用的）** | ❌ **没有** |

**同类错误在本项目出现了两次**（另一次是把 `alerts.csv` 误判成「规则基线」）。
**共同原因：读了数据集描述就下结论，没有先核对实际字段。**

**这正是 M1 存在的意义**——把「假设」变成「实测」。这个教训记录在案，也会写进面试手册。

## 5. 真值设计（**C 方案：原生 + 注入**）

### 5.1 原生部分（保证真实性）

| 我们设计的模式 | 对应原生标注 | 数量 |
|---|---|---|
| **P1 回流环路** | `ALERT_TYPE = cycle` | **936** |
| **P3 集中转入（扇入）** | `ALERT_TYPE = fan_in` | **783** |

**这两类是真值可信、无需我们构造的。**

### 5.2 注入部分（保证广度，真值可控）

在原生数据之上，**受控注入**以下模式。**真值就是注入的位置**——与产线项目的故障注入**同一套方法**。

| 模式 | 注入什么 | 为什么注入 |
|---|---|---|
| **P2 分层（stack）** | 构造"大额拆分 → 多层中转 → 汇聚"的路径 | 原生数据没有 |
| **P3 扇出（fan_out）** | 构造"一对多分散转出" | 原生只有 fan_in |
| **P4 同一控制人多账户** | **为部分客户生成第二个账户**，再构造两者间互转 | 原生 1:1，必须造 |
| **P5 失相关/噪声控制** | 注入**结构相似但不涉诈**的模式，作为**负例** | ⚠️ 见下 |

### ⚠️ 5.3 `P5 负例` 是这套设计里最关键的一环

**只注入"正例"是不够的**——那会让系统学会"看到环路就报警"，
而在真实数据里，**环路可能只是正常的资金周转**。

**必须同时注入"结构相似但正常"的负例**，用来测量：

> **系统能不能区分「看起来像洗钱」和「真的洗钱」。**

**这也是 Precision@K 这个指标真正要衡量的东西**——
如果只测"能不能找到环"，那把所有环都报出来就行了。

### 5.4 数据划分

| 集合 | 用途 | 构成 |
|---|---|---|
| **训练/开发集** | 调参、开发 | 原生 + 部分注入 |
| **测试集** | **只用于最终评测** | 原生 + 另一部分注入（**注入种子不同**） |
| **对照集（负例）** | 测误报 | 结构相似但不涉诈 |

⚠️ **划分必须按"注入种子"隔离，不能按行随机划分**——
否则注入的同一模式会同时出现在训练和测试里，**评测分数虚高**。

## 7. M1 结论

**可以做，但设计要求被数据修正了三处：**

1. **规模**：从「10 万节点 / 100 万边」修正为「**1 万节点 / 132 万边**」；
2. **模式**：从「P1–P4 全部原生支持」修正为「**P1 + P3(扇入) 原生，其余靠注入**」；
3. **时序**：从「快进快出检测」**降级**为「粗粒度分层时序」。

**这三处修正全部记录在 ADR-0004，并已回写 PRD。**

> **这就是真实项目的样子**——需求被数据现实修正，关键是你**记录它、说明理由**，
> 而不是**改数据去迁就需求**。
