## 13.1 先确定知识库的**合理规模**

选型之前必须先知道"要检索多少东西"。**否则"要不要向量数据库"只能靠感觉。**

### 来源必须可追溯

知识库是**领域知识**，不是我的想象。所以每一条都标了来源：

| 分组 | 条数 | 来源 |
|---|---|---|
| **图结构模式** | **8** | Altman et al. 2023, [arXiv:2306.16424](https://arxiv.org/abs/2306.16424), Figure 2 |
| **资金流转类型学** | **10** | FATF 三阶段框架（placement / layering / integration）+ 公开监管类型学 |

**合计 18 条。**

### 那 8 种图结构的原文定义

论文原话（「These 8 patterns are illustrated in Figure 2」）：

| 模式 | 定义 |
|---|---|
| `fan-out` | 顶点 `v` 的出边把它连到**至少 `k≥2` 个不同顶点** |
| `fan-in` | `v` 通过入边连到 `k≥2` 个不同顶点 |
| `gather-scatter` | **同一个顶点**上 fan-in 与 fan-out 的组合 |
| `scatter-gather` | `v` 的 fan-out 与 `u` 的 fan-in 连到**同一组**顶点 |
| `bipartite` | 一组输入账户 → 一组输出账户 |
| `stack` | bipartite **再加一层** bipartite |
| `cycle` | 资金从某账户出发，**最终回到同一账户**（论文称其为"强指示"） |
| `random` | 被控制账户间的随机游走 |

**这 8 种正是我们的数据集生成器所注入的模式**——
所以它们既是知识库条目，也是评测真值的语义标签。

### ⚠️ 一个我自己犯的错

第一版我在注释里写了「**22 条**」。**实际是 18 条。**

> **数字要说数过的，不是印象里的。**
>
> 修法不只是改数字——`scripts/build_pattern_index.py` 会**打印实际条数**，
> 而且注释里写明了"改这个文件要同步更新引用"。
> **让不一致在跑一次的时候就能被发现。**

### ⚠️ 来源写得笼统 = 没有来源

`test_every_entry_declares_a_source` 一开始只检查"非空"，
结果几条写着「监管类型学」——**5 个字，本质上就是"我没出处"**。

改成要求长度 + 具体性之后，那几条被逼着写清楚了。**而诚实的写法是**：

```yaml
source: >-
  行业通用金额特征指标（实务经验型判据，无单一权威出处）
```

> **把"没有单一权威出处"这件事写清楚，比拿一个笼统词糊过去强。**

## 13.2 嵌入：为什么必须做成**接口**

### 环境实测（决定了选型）

```text
Ollama 已安装，模型已就绪：
  qwen3:4b       2.5 GB   ← M5 的本地 LLM 也有了
  bge-m3:latest  1.2 GB   ← 嵌入模型

可达性：
  huggingface.co      ❌ 不通
  hf-mirror.com       ✅ 通
  registry.ollama.ai  ✅ 通

轻量方案对比：
  fastembed               ✅ 不依赖 torch
  sentence-transformers   ⚠️ 依赖 torch（约 2 GB）
  model2vec               ⚠️ 也依赖 torch
```

**选 Ollama + `bge-m3`**：零下载成本（已就绪）、零 API 成本、中文效果好、不用拖 torch。

### ⚠️ 性能实测：**"批量更快"这个直觉不成立**

```text
冷启动（模型首次载入）   25.8 秒   ← 只有第一次
热调用（单条）            0.41 秒
批量 20 条               10.56 秒   = 528 毫秒/条
```

**批量传 20 条，平均每条反而更慢**（528ms vs 440ms）。

**原因**：CPU 推理上每条文本是**独立编码**的，批量不会并行，
只多了序列化开销。**按 0.45 秒/条做容量规划才靠谱。**

> 这条值得记：**"批量调用能摊薄开销"是 GPU 批推理的直觉，不是 CPU 的。**

### 为什么嵌入层必须是接口

真实实现走 Ollama，但 **CI 里跑不了它**（要下 1.2 GB 模型、CPU 推理又慢）。

**如果测试直接依赖 Ollama，那些测试在 CI 里就会一直跳过——
而"一直跳过"等于没有测试。**

所以有两个实现：

| 实现 | 用途 | 特点 |
|---|---|---|
| `OllamaEmbedder` | 真实检索 | 本地推理，零 API 成本 |
| `HashingEmbedder` | **CI 与单元测试** | 确定性、无网络、毫秒级 |

**`HashingEmbedder` 不是随机数**：它用字符 n-gram 哈希，
所以**共享子串的文本相似度更高**。测试因此可以断言"相似文本得分更高"，
从而验证整条检索链路**真的在按相似度排序**，而不是只验证"函数能跑通"。

## 13.3 ⚠️ **不引入向量数据库**（测量后的决定）

```text
知识库            18 条
向量维度          1024
索引矩阵          18 × 1024 × 4 字节 = 72 KB
建索引（一次性）   14.4 秒
单次查询          约 0.5–2 秒（含编码，波动取决于 Ollama 状态）
一次全量余弦相似度 18 × 1024 = 1.8 万次浮点运算 —— 微秒级
```

**向量数据库是给「百万级向量 + 毫秒级召回」准备的。**
拿它检索 18 条数据：

- 多起一个进程；
- 多一份索引文件；
- **CI 里多一个要拉起来的服务**。

**这是"为了显得高级而引入的复杂度"。**

**但接口按"将来会长大"设计**：`retrieve.search()` 只依赖
「一个矩阵 + 一个查询向量」——真涨到几万条时，换掉这一处即可，**调用方不用动**。

> **面试时的说法**：
> 「我先量了知识库规模，18 条。**然后我没有引入向量数据库。**
> 它的适用场景是百万级向量，而这里是 72 KB、微秒级算完。
> 用它只是给自己加一个要维护的服务。
> **但我把接口设计成只依赖「矩阵 + 查询向量」——**
> 真长大了换实现就行，调用方一行都不用改。」

## 13.4 检索质量实测

用**真实模型**（`bge-m3`，不是哈希假实现）：

```text
查询：资金经过多个账户层层转移后回到起点

  1. 0.6662  [structural] 回流环路      ← 正确
  2. 0.6632  [structural] 多层堆叠
  3. 0.6545  [structural] 先散后聚
  4. 0.6392  [typologies] 快进快出
  5. 0.6380  [structural] 二分图转账
```

**Top-1 就是 `cycle`（回流环路）——完全正确。**

注意第 4 条：`快进快出` 来自**类型学**分组。
**结构模式与类型学混在同一个排序里**——这正是融合层要把它们分开处理的原因：
**一个回答"这是什么形状"，另一个回答"这在做什么"。**

### ⚠️ `min_similarity` 不是可选项

**余弦相似度永远会返回一个"最像"的结果，哪怕它一点都不像。**

没有下限的话，一个完全无关的查询也会拿到几条"匹配"，
然后它们会被当成证据拼进 LLM 上下文——**这就是幻觉的入口**。

有下限时，**返回空列表是有价值的答案**：
它说的是"**这不像任何已知手法**"，而不是"没查到"。

这与评测里的「未产出结论必须单独计数」是同一条原则。

### 关于零向量与 NaN

零向量的范数是 0，除它会得到 NaN——**而 NaN 会让排序变得不确定**
（比较结果全是 False，`sort` 的行为就依赖于实现）。

所以归一化时把零向量的分母换成 1，**让它的相似度恒为 0**（语义正确）。

### 关于 `test_yaml_files.py`（**本项目第三次踩 YAML 的坑**）

| # | 文件 | 写错的写法 | YAML 当成什么 |
|---|---|---|---|
| 1 | 上个项目的 `ci.yml` | `- name: ... (not committed: 5 MB)` | 冒号后是**映射值** |
| 2 | 本项目的 `ci.yml` | 开头写 `> **设计要点…**` | **块标量指示符** |
| 3 | **`knowledge/patterns.yaml`** | `definition: **同一个顶点**…` | **别名引用**（`*` 开头） |

三次都是同一件事：**用写文档的习惯写数据文件。**

**而前两次的检查只覆盖 `.github/workflows/*.yml`——第三次的漏洞就在没扫到的地方。**
现在扫的是**整个仓库**。

> 这和 `test_label_guard.py` 里那条教训完全一样：
> **没扫到的文件就是漏洞。**

**修法**：所有散文类字段一律用**块标量 `>-`**，
把文本原样保留，绕开 `*` / `&` / `: ` / `>` / `|` 所有这些陷阱。
