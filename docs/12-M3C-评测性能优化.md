# 12 · M3-C：评测性能优化（**372 秒 → 31 秒**）

> 这份文档单独成篇，是因为它示范的**方法**比结果更重要：
> **先量后改，而不是看着哪里慢就改哪里。**

## 12.1 为什么必须修

> **跑得慢的检查不会有人跑。** 28 分钟的评测等于没有评测——
> 每改一点东西就要等半小时，结果是"改完不验证"，而**不验证就等于不知道效果**。

而且它已经在 README 的「已知问题」里挂了很久。**知道问题却不修，比不知道更尴尬。**

## 12.2 先量，再改

**第一步不是优化，是加上分段计时。** 实测结果：

```text
  建字典  101.53 秒     ← 把 130 万条分数装进 Python dict
  排序     49.77 秒
  算指标   63.38 秒
  合计    214.67 秒     ← 评测循环
  整轮    372 秒        ← 其余是加载图、算特征、扫环
```

**如果不过这一关，最可能去优化"排序"——而它只占 23%。**

## 12.3 三处修改，每处都对应一个反直觉的发现

| 发现 | 修改 | 收益 |
|---|---|---|
| **瓶颈不是算法，是数据结构** | `Mapping[str,float]` → numpy 向量化快路径 | 214.7 → 5.5 秒 |
| **特征计算不需要图对象** | 去掉 `graph` 参数，改用 `value_counts` / `MultiIndex.isin` | ~31 → 1.6 秒（加载） |
| **`rank(pct=True)` 会排 6 列，只用 2 列** | 只对用得上的列算秩 | ~25 → 4.3 秒 |

#### 发现 1：指标层的瓶颈是数据结构

原本的接口是 `Ranking(scores=Mapping[str, float])`——
**130 万个字符串键的 Python 字典**，而且每个方法都要重建一次。

但指标的本质是「**排序 + 前缀和**」。一次排序、一次 `cumsum`，
所有按位置的指标都是 O(1)：

| 指标 | 式子 |
|---|---|
| 前 k 名里的正例数 | `cum_hits[k-1]` |
| 精确率@k | `cum_hits[k-1] / k` |
| 召回率@k | `cum_hits[k-1] / total_positive` |
| 达到目标召回要报多少条 | 在 `cum_hits` 上二分 |

**而且还顺带省掉了重复排序**：整体和分模式（`cycle` / `fan_in`）的排序完全相同，
只有标签不同——所以排序做一次，标签各算各的。

#### 发现 2：多传一个"看起来有用"的对象，可能只是在为它的构造成本买单

第一版签名是 `compute_edge_features(graph, edges)`。
但图对象只用来做三件事，**而这三件事边表里都有**：

| 要算什么 | 用图 | 用边表 |
|---|---|---|
| 出度 / 入度 | `dict(graph.out_degree())` | `edges["sender"].value_counts()` |
| 是否互转 | `set(graph.edges())` + Python 循环 | `pd.MultiIndex.isin` |
| 同一对的笔数 | — | `groupby().transform("size")` |

而**构建那个图对象要 30 多秒**（132 万条边逐条加进 NetworkX）。

**顺带发现的更根本的问题**：环检测本来就在**去重图**上做，
而**去重后只有 68,947 条边**（平行边占 94.8%）——
用 `load_simple_graph()` 而不是 `load_graph()`，这一步从 ~31 秒降到 0.3 秒。

#### 发现 3：白算的列

`two_detector_scores` 里写的是 `rank = features.rank(pct=True)`，然后取 `["pairTxCount"]`
和 `["amount"]` 两列——**那会对 6 列各排一次序，其中 4 次的结果直接扔掉**。

130 万行的 `rank(pct=True)` 是秒级的。**白算 4 列就是白花几秒。**

## 12.4 快路径的正确性怎么保证

**numpy 版本快，但只有在"和已验证的实现逐项一致"时才可以信任。**

`test_curve_matches_the_ranking_path` 用随机数据逐项比对两条路径，参数里包含：

- `tie_groups=1` —— **全部并列**（这正是实测踩过的场景：全图 24 万条边分数完全相同）
- `tie_groups=2/5/1000` —— 不同程度的并列
- 多个 `k` 值（1 / 2 / 7 / 50 / 300 / 500 / 1000）
- `precision_at_recall` 的多个目标（0.1 / 0.5 / 0.9 / 0.99 / 1.0）

**没有这个测试，快路径就是个隐患**——而且是那种"数字看起来很合理、但其实是错的"隐患。

## 12.5 结果

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 加载边表与数据 | ~31 秒 | **1.6 秒** |
| 算结构特征 | 5.3 秒 | **2.1 秒** |
| 扫环 | 2.6 秒 | **0.8 秒** |
| 构造分数 | ~25 秒 | **4.3 秒** |
| 特征方向评测（10 个） | — | 3.8 秒 |
| 最终对比评测（13 个） | **214.7 秒** | **5.5 秒** |
| **总耗时** | **372 秒** | **31 秒** |

**改动前后结果几乎不变**（差异全部来自并列键从字符串改成整数）：
`双检测器·求和` 的 P@100 仍是 **100.0%**。

## 12.6 面试讲法

> 「评测脚本原来要 28 分钟。**我没有直接去优化，先加了分段计时**——
> 结果发现瓶颈分布和我猜的完全不一样：
> **建字典 101 秒、排序 50 秒、算指标 63 秒**。
>
> 建字典最慢，说明**瓶颈不是算法，是数据结构**——
> 指标层原本围绕 130 万个字符串键的 Python 字典设计，每个方法都要重建一次。
>
> 改成向量化之后，**一次排序 + 一次前缀和覆盖全部指标**，214 秒变 5.5 秒。
>
> 然后我继续量，又发现**特征计算根本不需要图对象**——
> 它只用了度数和一个集合查询，而**构建那个图对象本身要 30 多秒**。
> 更根本的是：环检测本来就在去重图上做，**去重后只有 6.9 万条边**，
> 用多重图（132 万条）是白慢 19 倍。
>
> 最后是 `rank(pct=True)`——它会排 6 列，而我只用 2 列。
>
> **总耗时从 372 秒降到 31 秒。而每一步都是先量后改的**，
> 没有一步是"看着哪里慢就改哪里"。
>
> 快路径我加了逐项一致性测试，参数里特意包含**全部并列**的极端情况——
> 因为并列正是我之前踩过的坑。」
