# 14 · M5：Agent 编排

> **核心原则：**
> **「什么都没找到」和「根本没给答案」是两件完全不同的事。**
>
> 前者是**能力问题**——可以量化、可以改进；
> 后者是**工程缺陷**——它同时**压低检出率**、又**虚假地压低误报率**，
> **会让所有指标失真**。

---

## 14.1 开工前先测量（**最大未知是模型能不能调工具**）

上个项目的教训：**Agent 跑出 0% 检出率，看起来像"能力不行"，
实际是工具粒度 + 步数预算的问题。**

所以 M5 第一件事是验证本地 `qwen3:4b` 的工具调用能力。

### 工具调用：**稳定可用**

```text
第 1 次（66.4 秒）：investigate_account({'account_key': 'amlsim:4122', 'hops': 1})
第 2 次（57.0 秒）：同上
第 3 次（53.9 秒）：同上
→ 3/3 稳定，参数正确
```

### 而且验证了一个**设计假设**

不给工具时，模型是这样"给结论"的：

```text
没调工具，直接说话：submit_conclusion("信息不足，无法进行反洗钱分析。")
```

> **它「说」它调用了 `submit_conclusion`，但没有真的调用。**
>
> **这证明「用具不具备 `tool_calls` 来判断是否产出结论」是可靠的、
> 可数的、不会误判的。** —— 这正是「未产出结论必须单独计数」能落地的前提。

### 耗时：**不是 thinking 的锅**

```text
冷启动            54–66 秒
热调用            10–17 秒
think=False       17.2 秒    ← 反而比默认慢
/no_think（提示）   9.8 秒     ← 只快 1.3 倍
```

**thinking 开关收益很小**，真正的变量是**模型有没有热**。

> **按 15 秒/步做容量规划。**
> `max_steps=6` → 约 1.5 分钟/案例 → 30 个案例约 45 分钟。
> **这个数字直接约束了工具粒度：必须一次给够，不能靠加步数。**

### 一个意外的发现：`arguments` 传字符串会 **HTTP 400**

```text
assistant 消息里 arguments 用【对象】   → ✅ 正常
assistant 消息里 arguments 用【字符串】 → ❌ HTTP 400 Bad Request
```

**幸好我们塞回历史时用的是 Ollama 返回的原始对象。**
这条如果踩了，会表现为"模型突然开始返回垃圾"，而**极难定位**。

## 14.2 三个机制

### ① 用**工具调用**作为"是否给出结论"的判据

不解析模型输出的文本，而是看它**有没有真的调用 `submit_conclusion`**。

**这是"可数"的前提**——文本可以含糊，工具调用不会。

### ② 预留**强制产出步**

```text
第 1..N-1 步：4 个侦查工具 + 结论工具
第 N 步：    只有结论工具          ← 它没有别的选择
```

### ③ 三种异常**分别计数**，绝不合并

| 字段 | 含义 |
|---|---|
| `exhausted` | 步数耗尽，**从未产出结论** ← 工程缺陷 |
| `forced` | 结论来自强制产出步（说明自由步数不够用） |
| `premature` | **没做任何侦查就给结论** ← 实测发现模型会这样 |

`premature` 是实测发现的：问"介绍你自己"，它直接调了 `submit_conclusion`。
**不拦截它，但要计数。**

## 14.3 ⚠️ 真跑发现的缺陷：**"强制产出步"没有强制成功**

### 现象

```text
第 1 步（46.2 秒）→ investigate_account ✓
第 2 步（57.1 秒）  只说话（写了一大段分析）
第 3 步（24.6 秒）→ investigate_account(hops=2) ✓
第 4 步（32.0 秒）→ match_patterns（参数名记错）
                    ← [失败] 参数错误：structure_description 必须是非空字符串
第 5 步（32.0 秒）[强制产出步]  只说话（空的）
❌ 未产出结论（步数耗尽）
```

### 根因：**"提供"不等于"强制"**

我以为"只给它一个工具，它就只能用那个"——
**但模型完全可以什么都不调。**

> **设计意图是对的，实现没做到。**

### 诊断（先排除我怀疑的那条）

怀疑过"是不是我把 assistant 消息塞回历史的方式不对"。**测了一下，排除了**：

```text
场景 1：干净对话 + 只给结论工具
  arguments 用对象      → ✅ 2/2 调用了 submit_conclusion
  arguments 用字符串    → ❌ HTTP 400
```

**所以格式是对的。** 真跑失败是因为**对话很脏**
（长长一段"只说话"、一条失败的工具结果）。

### 修法

1. **强制步给有限次机会**（`FORCED_STEP_ATTEMPTS = 2`），
   第 2 次用**不容含糊**的措辞：

   > 「你还没有给出结论。**文字回复不算完成**——
   > 必须调用 `submit_conclusion` 工具……如果信息不足，
   > 就把 `suspicious` 填 false、`confidence` 填低，并在 reason 里说明缺什么。」

   **刻意不留余地**——温和的措辞正是第一次失败的原因之一。

2. 不给更多次，因为**每一步都花 10–17 秒**，
   而"它就是不配合"也是有效结论。

### ⚠️ 而兜底拿到的自由文本，**不算结论**

这是本次最重要的一条设计决定：

> 一段自由文本**没有 `suspicious`、没有 `confidence`**。
> 硬把它记成"结论：未发现异常"，就是本项目一直在反对的那种混淆：
> **"我看了，没问题"和"我没给出结论"会被算成同一件事。**

所以：

| 字段 | 处理 |
|---|---|
| `final_text` | **留着供人看**（写报告、排查为什么没结论） |
| `exhausted` | **仍然是 `True`** |
| `summary()` | **只报长度，不报内容**——避免它被当成结论读 |

## 14.4 修复后的成功案例

```
第 1 步（36.4 秒）→ investigate_account(hops=1) ✓
第 2 步（46.8 秒）→ submit_conclusion ✓

结论：可疑    置信度 0.85
理由：该账户在190天内向11个不同账户各发送20笔197.52元交易（共221笔），
      总金额43,454.4元，存在高频相同金额的分拆交易特征
      （每笔197.52元，时间跨度t=9..199）
```

**这是 `ALERT_TYPE=cycle` 的已确认洗钱案例——判定正确。**

而且它**真的引用了查到的数据**（11 个账户、各 20 笔、197.52 元、t=9..199），
不是空泛的"存在可疑迹象"。**这正是系统提示词里那条要求的体现。**

**2 步、83 秒完成**（对比修复前的 5 步、192 秒还失败）。

### ⚠️ 但两次的差别**有一部分是随机性**

Ollama 默认温度不为 0。上一次它 wandered 到 `hops=2` 和 `match_patterns`，
这次直接给了结论。

> **这意味着 Agent 需要更低的温度才能稳定。** 这是还没做的一件事。

## 14.5 工具设计：**粒度是刻意的**

上个项目里，诊断工具一次只能查**一个传感器**，
Agent 把 4 步预算全花在逐个查询上，**压根没走到给结论**。

所以：

| 工具 | 粒度 |
|---|---|
| `investigate_account` | **一次返回整个邻域**（按账户对归并，含笔数/金额区间/时间跨度） |
| `get_transactions` | 某一对账户之间的明细（需要时才用） |
| `trace_path` | 最短资金路径 |
| `match_patterns` | 语义匹配已知手法 |

**并实测到一次真实的"工具描述问题"**：模型把 `match_patterns` 的参数
传成了 `account_key` 和 `transaction_patterns`——**它把描述理解成了"按账户匹配"**。

> **这是工具描述的问题，不是模型的问题。**
> 参数名与描述要让它一眼看懂"这里要放一段自然语言"。

---

## 14.6 参数上界由**服务端**强制

`hops ≤ 3`、`top_k ≤ 5`、`limit ≤ 500`、`max_length ≤ 8`
（工具契约见 `docs/06`）**不是"建议"**：

> **提示词挡不住一个跑飞的 Agent。** 邻域随跳数指数增长，
> 一个 `hops=10` 的请求就能把内存打满。

**而参数错误要返回给模型让它自己纠正**，不是抛异常中断循环——
抛异常会把"模型犯了个小错"升级成"整个案例失败"。

**实测印证**：第 4 步那个错误的 `match_patterns` 调用，
返回了 `参数错误：structure_description 必须是非空字符串`，
而循环继续跑下去了。
