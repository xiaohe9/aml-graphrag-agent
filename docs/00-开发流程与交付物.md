# 00 · 开发流程与交付物

> 这份文件是**我们这个项目的作业规程**。它同时也是一件"内功"装备：
> 面试时被问到"你们公司一个项目怎么做"，你照着这条线讲，就是**标准答案**。

---

## 一、为什么要按流程走

**因为面试官问的"深度"，问的就是流程里的决策点。**

一个没走过流程的人，被问到这些只能编：

- "你这个需求哪来的？"
- "为什么选图数据库不用现成的向量库？"
- "你怎么知道它做完了？"
- "上线出问题怎么办？"

一个走过流程的人，每个问题背后都有一份文档。**文档不是形式，是你思考过程的证据。**

---

## 二、七个阶段（真实公司的做法）

```text
① 需求  →  ② 设计  →  ③ 开发  →  ④ 测试  →  ⑤ 部署  →  ⑥ 运维  →  ⑦ 迭代
   ↑                                                                    │
   └──────────────────────  复盘、反馈  ────────────────────────────────┘
```

### ① 需求阶段

| 做什么 | 具体动作 |
|---|---|
| 找干系人聊 | 谁是用户、谁付钱、谁会被影响 |
| 搞清现状 | 他现在怎么做这件事？痛在哪？ |
| 分清三层需求 | 业务需求 → 用户需求 → 功能需求（见下） |
| 划范围 | 做什么、**明确不做什么** |
| 定验收标准 | 什么算做完了 |
| **需求评审** | 拉相关人确认，签字 |

**产出**：PRD（产品需求文档）、SRS（需求规格说明书，可测试）
**面试官会问**：需求从哪来？谁提的？你怎么排优先级？

### ② 设计阶段

| 做什么 | 具体动作 |
|---|---|
| 概要设计 (HLD) | 架构图、模块划分、技术选型 |
| 详细设计 (LLD) | 接口定义、数据模型、关键算法、异常处理 |
| **决策记录 (ADR)** | 每个重要选择：考虑过什么、为什么选这个 |
| **设计评审** | 拉人挑战你的方案 |

**产出**：HLD、LLD、ADR
**面试官会问**：为什么这么选？还考虑过什么？瓶颈在哪？

> **ADR 是被最多人忽略、又最能体现深度的一份文档。** 它记录的是"**我为什么不选另一个**"——这正是面试官最爱问的。

### ③ 开发阶段

| 做什么 | 具体动作 |
|---|---|
| 任务拆分 (WBS) | 把设计拆成可交付的小块 |
| 排期 | 每块几天，依赖关系 |
| 接口先行 | 前后端先定接口，再各写各的 |
| 分支策略 | 主干 + 特性分支，或 trunk-based |
| Code Review | 别人看你的代码 |
| 单元测试 | 边写边测 |

**产出**：可运行的代码、单测、提交历史
**面试官会问**：任务怎么拆的？代码怎么保证质量？

### ④ 测试阶段

| 做什么 | 具体动作 |
|---|---|
| 测试用例 | 每个功能需求对应至少一个用例 |
| 集成测试 | 模块拼起来能跑 |
| **效果评测** | ⚠️ **AI 项目特有**：不是"功能通了"，是"准确率达标" |
| 性能测试 | 响应时间、并发 |
| 验收测试 | 按 SRS 的验收标准逐条过 |

**产出**：测试用例、评测报告、Bug 列表
**面试官会问**：你怎么证明它有效？跟什么比？

> ⚠️ **这是 AI 项目和普通项目最大的区别。** 普通项目"功能跑通 = 完成"；AI 项目必须回答"**效果好到什么程度，跟什么基线比**"。
> **这也是你的强项**——上一个项目你已经做过一次故障注入评测了。

### ⑤ 部署阶段

| 做什么 | 具体动作 |
|---|---|
| 环境分离 | dev / test / prod |
| CI/CD | 提交自动跑测试、自动构建 |
| 容器化 | 一条命令起全栈 |
| 灰度/回滚 | 出问题怎么退回去 |

**产出**：Dockerfile、CI 配置、部署文档
**面试官会问**：怎么上线的？出问题怎么回滚？

### ⑥ 运维阶段

监控、告警、日志、复盘。
**（你的 15 年老本行，这部分你是专家。）**

### ⑦ 迭代阶段

根据反馈改需求，回到 ①。
**面试官会问**：上线后发现了什么问题？怎么改的？

## 三、需求的三层（这一层最容易讲错）

很多人说"需求"就是"要做什么功能"。**错。** 真实的需求有三层：

```text
业务需求（Business）    ── 为什么公司要做这件事？目标和收益是什么？
        ↓
用户需求（User）        ── 用户想达成什么目的？（不是想要什么功能）
        ↓
功能需求（Functional）  ── 系统具体要提供什么能力？
        +
非功能需求（Non-Functional） ── 性能、安全、可解释性、合规……
```

**举例（本项目的）：**

| 层次 | 内容 |
|---|---|
| 业务需求 | 降低反洗钱人工排查成本，提高可疑交易检出率，减少监管处罚风险 |
| 用户需求 | 分析师希望**不用自己翻几十张表**，就能知道"这个账户周边有没有问题、证据是什么" |
| 功能需求 | 图谱构建、环路检测、社区发现、GraphRAG 检索、Agent 问答、证据回链 |
| 非功能需求 | 单次查询 < N 秒；结论必须可追溯到原始交易（**合规硬要求**）；本地可部署 |

**面试陷阱**：面试官问"你的需求是什么"，如果你直接答"做一个 GraphRAG 问答系统"，他会立刻判定**你把功能当成了需求**。

**正确的答法**："业务上要降低人工排查成本，用户是反洗钱分析师，他们的痛点是……所以系统需要具备……" —— **从业务往下讲，不是从功能往上讲。**

## 四、需求从哪来（真实做法）

| 方式 | 说明 |
|---|---|
| **干系人访谈** | 直接问用户、问业务方 |
| **现状调研** | 看他现在怎么做，跟着走一遍流程 |
| **痛点挖掘** | 问"最烦的是哪一步""哪一步最容易出错" |
| **标杆对照** | 同行怎么做？监管要求是什么？ |
| **数据反推** | 看现有数据能支撑什么 |

⚠️ **本项目是个人项目，没有真客户。** 但这**不妨碍我们走流程**——做法是：
**用公开资料建立"用户画像"**（FATF 反洗钱指引、银行合规岗的公开职责描述、行业报告），
然后像真实项目一样写 PRD。

**面试时诚实说**："这是我自己的项目，用户画像基于公开的行业资料和监管要求，不是真实客户访谈。"
——**这比假装有客户更可信**，而且展示了你知道真实流程长什么样。

## 六、每个阶段的固定动作（我们的协作方式）

```text
1. 我讲这个阶段在做什么、为什么（大白话）
2. 我把决策点摆出来，给选项 + 各自代价
3. 你选，并说出理由
4. 我把你的选择写成文档
5. 你复述给我听，我挑你讲不清的地方
6. 你说"过"，才进入下一阶段
```

**第 3 步和第 5 步是关键**——它们是把"我做的项目"变成"你的项目"的唯一机制。
