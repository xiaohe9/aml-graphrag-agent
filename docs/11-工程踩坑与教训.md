## 1. `.gitignore` 的 `data/` 吞掉了源码包

**这是最有价值的一条**——它让 CI 第一次运行两个 job 全红。

### 症状

```
checks job:        ModuleNotFoundError: No module named 'aml_agent.data'
                   mypy: Cannot find implementation for module "aml_agent.data"
integration job:   建图失败（同一个 import 错误）

注意：`aml_agent` 能导入，但 `aml_agent.data` 不能。
```

### 根因

```gitignore
data/        ← 本意：排除根目录的数据集
               实际：匹配【任意层级】的 data 目录，包括 src/aml_agent/data/
```

```text
$ git check-ignore -v src/aml_agent/data/schema.py
  .gitignore:9:data/    src/aml_agent/data/schema.py

$ git ls-files src/aml_agent/
  detect/  eval/  graph/  ...      ← 没有 data/
```

**`schema.py` 和 `loader.py` 从来没被提交过。**

### 为什么本地永远发现不了

**磁盘上文件都在。** 跑测试、跑建图、跑评测，全部正常——
因为 Python 从文件系统读，不从 git 读。

**只有新克隆的仓库里才会暴露。** 而 CI 恰好就是新克隆。

> **这是"在我机器上能跑"的纯粹形态。**
> 如果没建 CI，这个项目推上去后**任何人 clone 都会 import 失败**，
> 而我可能很久都不知道。

### 修法

```diff
- data/          + /data/
- _probe/        + /_probe/
- artifacts/     + /artifacts/
```

（`__pycache__/`、`.venv/` 这类缓存目录**故意不锚定**——出现在哪一层都该被忽略。）

### 加的测试（三个，互补）

| 测试 | 抓什么 | 性质 |
|---|---|---|
| `test_gitignore_root_patterns_are_anchored` | **模式写法**有问题 | **主动** |
| `test_no_source_file_is_silently_ignored` | 磁盘上有、但**从没被 add** | 被动 |
| `test_every_package_under_src_has_tracked_files` | 包目录存在却**一个文件都没入库** | 反面 |

**前两条为什么都要**：`.gitignore` **管不到已跟踪的文件**。
所以只靠第二条会漏掉"模式已经写坏、只是碰巧还没有同名源码目录"这种情况。

**做了反向验证**：把 `data/` 改回去 → 第一条立刻变红 ✅

### 教训

> **`.gitignore` 的匹配规则不看意图，只看模式。**
> 一句看起来无害的 `data/` 就能吃掉一个源码包。
>
> **靠人记住"这个模式会不会误伤"是不可靠的**——必须有自动化检查。

## 2. YAML 里 `>` 不是注释

### 症状

CI 完全不跑——但**没有任何报错**，只是"没有运行"。

### 根因

```yaml
> **这个文件的设计要点：CI 跑的命令，就是本地跑的命令。**

# 门禁清单写在 scripts/check.py 里…
```

**`>` 在 YAML 里是块标量指示符**，不是 Markdown 引用。整个文档解析失败，
**GitHub 整份拒收 workflow**——于是每次推送的每一个 job 都失败，**而且从没运行过**。

### ⚠️ 同一个错误犯了两次

上一个项目里是另一句：`- name: Fetch SECOM (not committed: 5 MB …)`——
未加引号的标量里含 `": "`，同样让整个 workflow 失效。

**而当时我用 `Select-String`（正则）"检查"过，它显示没问题。**

### 修法

**用真正的 YAML 解析器检查**（`tests/test_workflows.py`），并额外查三件解析器管不了的事：

| 检查 | 为什么语法解析发现不了 |
|---|---|
| 有 `on:` 触发条件 | 没有它 workflow **永远不跑**，而"永远不跑"和"跑失败"在页面上看起来完全不同 |
| 每个 job 有 `runs-on` | 语法上合法，但 GitHub 会拒收 |
| CI 调用了 `scripts/check.py` | 防止 CI 和本地**各自演化** |

### 教训

> **正则不是解析器。** 它只能看到你想到的模式，看不到语法本身错了。
>
> **验证要用和真 parser 同级的工具** —— 检查 YAML 就用 YAML 解析器，
> 检查类型就用类型检查器。**降级检查 = 假的安全感。**

## 3. `nx.simple_cycles` 跑不完 ≠ 环枚举不可行

### 症状

```text
去重图（68,947 条边）上的环枚举：
  长度 ≤2：  1,544 个环，  0.7 秒  ✅
  长度 ≤3：    145 个环，120 秒触顶  ❌
```

**69,000 条边的图，120 秒只找到 145 个三角形——这个数字本身就不合理。**

### 根因

**问题不在图，在那个函数的实现。**
`nx.simple_cycles(length_bound=...)` 用的算法在带长度限制时效率很差。

### 修法

自己实现：对每条边 `u→v`，用**集合求交**求从 `v` 回到 `u` 的最短路径：

| 回程 | 环长 | 判断 |
|---|---|---|
| 1 | 2 | `u ∈ 出邻居(v)` |
| 2 | 3 | `出邻居(v) ∩ 入邻居(u) ≠ ∅` |
| 3 | 4 | `∃w ∈ 出邻居(v)`：`出邻居(w) ∩ 入邻居(u) ≠ ∅` |

**结果：3.3 秒扫完全图。**

### 差点造成的后果

我在 M3 里写下过结论：「**全局环枚举不可行**」。
**这个结论下早了**——如果就此打住，「第二层定向深挖」这个设计就永远只是个说法。

### 教训

> **「某个库的某个函数做不到」不等于「这件事做不到」。**
>
> 而且**反常的数字要追**：「69,000 条边找 3 环要 120 秒」这件事本身就不对劲，
> 顺着它查才发现是库的问题，不是问题的难度。

## 4. `MultiDiGraph` 是 `DiGraph` 的子类

### 症状

单元测试 `test_parallel_edges_do_not_change_the_cycle` 失败：

```text
assert 3 == 29      # 期望扫 3 条去重边，实际扫了 29 条
```

### 根因

```python
simple = graph if isinstance(graph, nx.DiGraph) else nx.DiGraph(graph)
```

**`MultiDiGraph` 是 `DiGraph` 的子类**，所以 `isinstance` 对它也返回 `True`——
**去重被整个跳过**。

实测平行边占 **94.8%**，所以这个 bug 让扫描量变成 **19 倍**。

### 修法

```python
simple = nx.DiGraph(graph) if graph.is_multigraph() else graph
```

用 `is_multigraph()` 这个**语义化**的判断，而不是类型判断。

### 教训

> **`isinstance` 在有继承关系的类型上会骗你。**
> 想判断"它是不是多重图"，就问 `is_multigraph()`；
> 别用"它是不是某个基类的实例"来近似——**子类关系会让近似失效**。

## 5. `R@100 = 14.7%` 但它不可能是 14.7%

### 症状

第一版评测里，`仅互转` 这个方法报出 `R@100 = 14.7%`。

### 为什么一眼就知道错了

> **14.7% × 1,719 = 253 条。而前 100 名里最多只有 100 条。**

**这个数字自相矛盾。**

### 根因

我用「分数 **≥ 第 k 名的分数**」当阈值切。
而**全图有 242,981 条互转边的分数完全相同**（都是 1.0），
所以这一刀实际报出了 **24 万条**，不是 100 条。

### 修法

新增 `confusion_at_k()`——**按位置切，不按分数切**。

| 切法 | 含义 | 何时不同 |
|---|---|---|
| 按分数 | 「分数超过这条线的都报」 | **有并列时，报出的数量不可控** |
| **按位置** | 「**只看前 k 条**」 | 对应分析师的真实约束 |

**已写进测试锁住**：`test_confusion_at_k_slices_by_position_not_by_score`。

### 教训

> **自相矛盾的数字是 bug 的线索，不是"结果不太好"。**
> 「前 100 名里装不下 253 条」这种事，只有**停下来算一下**才能发现。
>
> 而且：**并列分数是评测里一个非常隐蔽的坑**——
> 在没有并列的数据上，两种切法完全等价，**测试根本发现不了**。

## 6. 隧道把本来能用的连接换成了坏的

### 症状

```text
git push 直连：  Failed to connect to github.com port 443 after 21081 ms
git push 隧道：  OpenSSL SSL_read: SSL_ERROR_SYSCALL, errno 0
```

**两条路都失败，而且报的是不同的错。**

### 根因

```text
隧道日志：tunnel -> 140.82.121.3:443      ← 它总是选这个 IP
实测：    140.82.121.3  能完成 TCP 握手，但 TLS 会被丢掉
          其余 5 个 IP  都正常
直连测试：Invoke-WebRequest https://github.com/... → ✅ 200
```

**隧道以为连上了**（`socket.on("connect")` 触发了），**把坏连接交给 git**。

> **隧道把本来能用的直连换成了坏的——比没有隧道更糟**，
> 因为它会让人以为是网络断了，去排查错误的方向。

### 修法

1. 把坏 IP 从候选列表移除；
2. **直连 4 秒推完。**

### 教训

> **TCP connect 成功 ≠ 连接可用。** 真正的判据是"能不能完成一次 TLS 握手"。
>
> **中间层故障会让错误信息指向错误的方向**——
> 隧道把"某个 IP 的 TLS 坏了"翻译成了"git 连不上 GitHub"。
> 排查时要**逐层验证**，别只看最外层的报错。

## 7. "本该慢的步骤异常地快结束" = 它崩了

### 症状

CI 的 `checks` job **整个只用了 16 秒**。而本地同样的门禁要 **67 秒**。

### 关键推理

> **16 秒不可能跑完四道门禁。**
> 所以它**不是"跑完发现失败"，而是中途就死了**。

这个判断把排查方向从"哪个测试挂了"改成了"脚本为什么异常退出"。

### 修法

顺着这个方向去拿日志，一次就定位到 `ModuleNotFoundError`。

### 教训

> **时长的异常本身就是一个信号。**
> 一个本该跑 60 秒的步骤 16 秒就"失败"了——它多半是崩了，不是跑完了。
>
> **先看"这个时长合不合理"，再看"错在哪"。**

## 8. Neo4j 事务内存：`MATCH (n) WITH n LIMIT 10000 DETACH DELETE n` 会爆

### 症状

```text
Neo.TransientError.General.MemoryPoolOutOfMemoryError
The allocation of an extra 24.0 MiB would use more than the limit 1.4 GiB
```

### 根因

**「1 万个节点」不等于「1 万次删除」。**
这里平均每个节点挂着 264 条边，于是"删 1 万个节点"
实际是**在一笔事务里删 130 万条关系**。

而 Neo4j 的**事务内存上限是固定 1.4 GiB，跟堆大小无关**——
所以调大 `heap_max` 是没用的。

### 修法

```cypher
MATCH (n)
CALL { WITH n DETACH DELETE n } IN TRANSACTIONS OF 500 ROWS
```

**分批的单位是「事务」，不是「循环」。**

### 教训

> **"分批"这个词很容易被误解成"在代码里写个循环"。**
> 真正的分批是**让每一批各自提交**——只有这样内存占用才有上界。
>
> 而且：**先查清限制是"每事务"还是"全局"**。
> 这里调大堆内存是无效操作，因为瓶颈根本不在堆。

## 9. 沙箱：判据不是"能不能写"，是"谁在写"

### 症状

```text
uv lock  → 项目目录    ❌ 拒绝访问 (os error 5)
Copy-Item → 项目目录    ✅ 成功
```

**同一个目录、同一个用户，一个能写一个不能。**

### 排查过程（排除了三个错误假设）

1. ❌ 不是文件权限——把权限补成和另一个目录一样，**依然失败**
2. ❌ 不是点开头目录的问题——非点目录一样失败
3. ✅ **是沙箱按「路径」限制子进程**

### 根因

> **判据不是"能不能写"，而是"谁在写"。**
> PowerShell cmdlet 跑在**我的进程**里，而 uv 是**被派生的子进程**，
> 拿到的是受限令牌。

### 修法

用「**在可写处生成、再用 `Copy-Item` 拷回来**」的办法绕过。

### 教训

> **同一个操作，由不同主体执行可能有不同结果。**
> 报"权限不足"时，先问一句：**是谁在请求？**
>
> 另外：**排除法要真的去排除**——我一开始的三个假设都是错的，
> 是把它们逐个证伪之后才找到真正的原因。

## 总结：这些坑有什么共同点

| 共同点 | 体现 |
|---|---|
| **都不是"不会写代码"，是"假设错了"** | 假设 account 有银行字段、假设 alerts 是规则基线、假设互转是强信号、假设 `data/` 只匹配根目录 |
| **都靠「测量/对照」发现，靠「想」发现不了** | 数据画像、特征选择表、反向验证、时长对比 |
| **都有一个"应该觉得不对劲"的数字** | 253 条装不进前 100、69,000 边找 3 环要 120 秒、16 秒跑完 60 秒的门禁 |
| **修完之后都留了自动化防线** | 测试、审计、CI——**不靠"下次记得"** |

> **能被追问的不只是"我做了什么"，更是"我怎么知道我做对了"。**
