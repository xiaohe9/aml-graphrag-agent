## 2. 项目背景与目标

### 2.1 业务背景

【我来写，基于公开资料：反洗钱的监管要求、银行的合规成本、现有规则引擎的局限】

### 2.2 问题陈述

> **反洗钱分析师**在**日常告警排查**中，被规则引擎产生的大量**误报**淹没；现有规则只看**单笔交易**，
> 而洗钱的痕迹在**资金路径**上。所以规则既容易漏掉真正的可疑行为，又对正常交易频繁误报。
> 代价是：分析师的时间被消耗在无效告警上，真正的可疑案件反而可能被埋没。

**关键归因（面试时的核心论点）：**

> **误报的根源是「规则只能看单笔交易」，而洗钱的痕迹在「路径」上。**
> 只有把账户和转账看成图，才能看到环路、团伙这类**结构性的**可疑特征。

### 2.3 三个候选痛点的分析（决策过程存档）

| 痛点 | 性质 | 能解决吗 | 能量化吗 | 定位 |
|---|---|---|---|---|
| **A. 报警多、误报高** | 痛点 | ✅ 图算法看模式，规则只看单笔 | ✅ 极易（注入真值） | **主痛点 → 主指标** |
| **B. 每条要翻十几张表、2 小时** | 痛点 | ✅ Agent 问答替代人工拼表 | ❌ 个人项目难证伪 | **用户场景 + 演示主线** |
| **C. 说不清推理过程** | **约束** | ✅ 证据回链 + 推理可回放 | ⚠️ 部分（覆盖率） | **硬约束 → 非功能需求** |

**决策记录：C 不是「第三个痛点」，而是「约束」。**
一个说明不了推理过程的结论，**根本进不了上报材料**，再准也没用。
因此它从痛点排序中移出，升格为非功能需求（见第 6 节）。

**类比（便于面试讲解）**：
「告警太多」和「告警没有上下文」都是**痛点**，可以改善；
但「**点开告警必须能看到原始指标**」不是第三个痛点，是**约束**——没有它，前两个改善都没意义。

### 2.4 业务目标（可量化）

⚠️ **主指标是一对数，不是一个数。** 理由见下方「指标对齐」与「两个切点」。

| 目标 | 定义 | 目标值 | 性质 |
|---|---|---|---|
| **主指标 ①** 固定召回下的精确率 | 把阈值放宽到**召回率 = 90%**，此时的精确率 | 【④测试阶段定】 | 设定值 → 实测值 |
| **主指标 ②** Precision@K | 排序前 K 条的精确率（K 按"分析师一天能看的量"设定） | 【④测试阶段定】 | 设定值 → 实测值 |
| 单次分析耗时 | 对比人工翻表流程 | **不设为指标**，仅作演示 | 个人项目无法诚实测量 |

**术语精确（面试会加分）**：

```
召回率 Recall    = TP / (TP + FN)     ← 分母是「所有真的洗钱」＝ 检出率
精确率 Precision = TP / (TP + FP)     ← 分母是「所有报出来的警」
误报率 FPR       = FP / (FP + TN)     ← 分母是「所有正常交易」
```

⚠️ **AML 行业口语说的「误报率 95%」，通常指 `1 − 精确率`，不是统计学的 FPR。**
两个词必须分清，否则面试时会被抓。

**指标对齐（重要决策）**：

痛点是「误报多」（A），而最初把主指标定为「检出率」——**两者方向相反**：
只看检出率，**把所有账户标红即可拿满分**，而这会让痛点更严重。

**最终决策：两个主指标必须同时报告**，并明确：

> **不接受用误报去换检出。**

**两个切点，同一个排序（设计含义）**：

```text
分数高 ┃████████████  ← 取前 K 个算精确率        → 指标 ② Precision@K
      ┃████████
      ┃██████        ← 放宽到召回 90%，算精确率   → 指标 ①
      ┃████
分数低 ┃██
```

两个指标**不是两套系统，是同一个排序的两种读法**：

| 指标 | 回答的问题 | 谁关心 |
|---|---|---|
| ① 固定召回下的精确率 | **如果不许漏**，误报会多到什么程度 | 合规 / 监管视角 |
| ② Precision@K | **分析师一天看 K 条**，效率如何 | 业务 / 人力视角 |

**→ 由此推出的一条硬性设计约束：系统必须输出「可排序的分数」，不能只输出「可疑/不可疑」。**

**诚实说明**：这是个人项目，上表的目标值是**设定值**，实测值在 ④ 测试阶段产生。

## 3. 用户与场景

### 3.1 用户画像 ✅ 已定

**主用户：反洗钱分析师**

**准确画像**（不要说"不懂技术"，那不准确）：

> **懂业务、会用工具，但不会写图查询语言、不懂图数据库。**

**从画像推导需求（这一步就叫「需求分析」）**：

| 画像特征 | 推导出的需求 |
|---|---|
| 不会写 Cypher / Gremlin | **必须自然语言入口**，不能给查询框 |
| 看得懂业务指标，看不懂「节点中心度 0.87」 | 结论必须是**业务语言 + 具体证据** |
| 结论要写进上报材料 | **每条结论必须能回链到原始交易** → 非功能硬约束 |
| 每天面对大量告警 | 入口要支持「**这个账户周边有没有异常**」这类开放式提问 |

**决策记录**：选非技术用户是**主动选择**，代价是
**证据的呈现方式与算法同等重要**。这个代价被接受，因为它把「证据回链」提升为 P0。

### 3.2 典型场景（用户故事）

【格式：作为<角色>，我希望<做什么>，以便<达成什么目的>】

**示例（待你确认或改写）：**

## 4. 范围

### 4.1 做什么（In Scope）✅ 已定

| # | 内容 | 为什么不能砍 |
|---|---|---|
| **S1** | 交易网络图谱构建（账户 / 转账 / 企业关系） | 地基 |
| **S2** | 图算法：环路检测 / 社区发现 / 中心度 | 「图」的价值所在 |
| **S3** | GraphRAG 混合检索（图 × 向量） | JD 明确要求 |
| **S4** | Agent 自然语言问答 | 砍了只是算法，不是 AI 应用 |
| **S5** | 证据回链到原始交易 | 硬约束 C，砍了违反需求 |
| **S6** | 三层评测体系 | 砍了项目没价值 |
| **S7** | 前端可视化（图谱 + 证据）——**做，但简化** | 「证据看得见」不能砍 |
| **S8** | 推理轨迹可回放 | **本期不做**（与 S5 有重叠，先保证据回链） |

**决策记录**：S1–S6 是一个**互相支撑的整体**——砍任何一项都会让其余几项失去意义。
S7 简化（不做复杂交互，只做"能看见图 + 能点开证据"）；S8 推迟。

### 4.2 **明确不做什么（Out of Scope）** ✅ 已定

> ⚠️ **这一节比 4.1 更重要。** 面试官特别爱问「你这个项目的边界在哪」。
> **写不出"不做什么"，等于没想过范围。**

| # | 不做什么 | 理由（**这就是面试答案**） |
|---|---|---|
| **O1** | 真实银行系统对接 | 无生产数据权限；以公开数据验证**方法**而非接入 |
| **O2** | 模型指令微调 | 投入产出比低；FDE 场景以**集成与调优**为主，不以训练为主 |
| **O3** | 实时流式检测 | 批处理即可回答「误报率高」这个问题；实时会成倍增加复杂度，而收益不明 |
| **O4** | 监管上报材料自动生成 | **上报是合规责任，必须由人完成**；系统只负责把证据准备到人可直接用的程度 |
| **O5** | 多租户 / 权限体系 | 个人项目，无组织隔离需求 |
| **O6** | 反洗钱以外的金融场景（信贷、投顾…） | **聚焦一个场景才能做深** |
| **O7** | KYC / 客户尽调流程 | 与可疑交易识别是不同问题域 |
| **O8** | 移动端 | 分析师在 PC 上工作 |
| **O9** | 图数据库分布式 / 集群部署 | 单机规模足够；**先证明方法有效，再谈规模** |

**⚠️ O4 的表述要小心**：

说「不做自动上报」是对的，但**别让人误以为「可解释性也不重要」**。正确说法是：

> 「我不做自动上报——**上报是合规责任，必须由人做**。但正因为要由人做，
> **系统必须把证据准备到人可以直接用的程度**，所以证据回链是 P0。」

**这一句同时做到了「划边界」和「强化重点」。**

## 6. 非功能需求 ✅ 已定

| 类别 | 要求 | 依据 / 后果 |
|---|---|---|
| **性能（分级）** | **简单查询 ≤ 30 秒；深度分析 ≤ 2 分钟** | 本地模型一次调用 5–20 秒，多步 Agent 必然慢。**分级 SLA 是对现实的承认，不是妥协** |
| **规模** | **1 万节点 / 132 万边**（⚠️ 原定十万节点，M1 数据实测后修正，见 ADR-0004） | → **仍建议图数据库（Neo4j）**：**边数是图遍历的主要成本，而它超过百万**；且目标公司主业是图数据库 |
| 可解释性 | 每条结论可追溯到原始交易 | **合规硬要求**（约束 C） |
| **可排序输出** | 系统必须输出**可排序的分数**，不能只输出「可疑/不可疑」 | 由指标 ① ② 反推得出（见 2.4） |
| 人工在环 | 系统是**排序 + 解释**工具，不是判断工具；决定权在人 | 合规责任不可转移 |
| 部署 | 本地可跑，Docker 一键启动 | 演示与可复现 |
| 成本 | 全程本地模型，**零 API 花费** | 硬约束，直接影响模型选型 |
| 数据 | 公开数据，无隐私合规风险 | — |
| 可复现 | 同一输入结果可复现 | 评测需要；也是"不是演示品"的证据 |

### 6.1 三条"约束驱动设计"（面试核心论据）

⚠️ **这张表里的"性能 / 规模 / 成本"三条不是凑数的**，它们**反向决定了技术选型**：

| 约束 | 推导出的设计决策 |
|---|---|
| **零 API 成本** | 全程本地模型（Ollama）→ 影响模型大小选择 → 影响响应时间 |
| **规模十万级节点** | **必须用图数据库**，不能用 NetworkX 内存图 |
| **简单查询 ≤ 30 秒** | 轻量问题**不能走多步 Agent**，必须有快速通道（直接检索） |

**面试话术：**

> 「我先定了三条硬约束：零 API 成本、十万级节点、30 秒响应。
> **这三条反过来决定了我的技术选型**——必须本地模型、必须图数据库、必须有快速通道。
> 我是**先定约束再选型**，不是有什么用什么。」

**这句话的分量比任何技术细节都重。**

### 6.2 为什么规模选 B 是**战略**选择（不只是技术）

> **海致卖的就是图数据库。**
> 如果用 NetworkX（一个 Python 库）做完整个项目，面试官会想：「**他没用过真正的图数据库。**」
> 用上 Neo4j，才能讲 Cypher、索引、查询计划——**那才是他们的日常。**

**规模定小了，就体现不出「图数据库」这项能力。** 这是一个战略性的选择。
