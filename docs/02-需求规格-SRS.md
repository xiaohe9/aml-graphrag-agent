# 02 · 需求规格说明书（SRS）

> **PRD 回答「要做什么、为什么」；SRS 回答「怎么算做完了」。**
>
> SRS 的每一条都必须是**可测试的**。测不了的条目不是规格，是愿望。
>
> **面试时被问「你怎么知道做完了」——翻这一页。**

---

## 一、功能需求（FR）

### FR-1 交易网络图谱构建

| 项 | 内容 |
|---|---|
| **描述** | 从原始交易数据构建图：`Account`、`Entity` 节点；`TRANSFER`、`CONTROLS` 关系 |
| **输入** | 交易流水文件、账户映射文件 |
| **输出** | Neo4j 中已建索引的图 |
| **验收标准** | ① 节点数、边数与源数据行数**对得上**（可脚本核对）<br>② `Account.key = {bank}:{account_number}` **唯一**，无重复节点<br>③ 跨行同名账号**未被合并**（构造用例验证）<br>④ 4 个索引全部建立且被查询计划使用 |
| **实测方式** | 建图后跑一致性校验脚本 + `EXPLAIN` 查索引命中 |

### FR-2 侦查（`investigate`）

| 项 | 内容 |
|---|---|
| **描述** | 给定账户，一次调用返回该账户周边的汇总情报 |
| **输入** | `account_key`, `hops`（**≤ 3**，见 NFR-1） |
| **输出** | 邻域规模、环路候选、社区紧密度、枢纽排名、时间跨度 |
| **验收标准** | ① 单次调用 ≤ **10 秒**（hops=2，十万节点规模）<br>② 输出为**结构化 JSON**，字段齐全<br>③ 邻域为空时返回**明确的空结果**，不是异常 |
| **实测方式** | 计时脚本 + schema 校验 |

### FR-3 资金环路检测

| 项 | 内容 |
|---|---|
| **描述** | 检测资金回流环路 |
| **输入** | 起点账户、最大环长（**≤ 8**） |
| **输出** | 环路列表（涉及账户、金额、时间、环长） |
| **验收标准** | ① 对**数据集自带的 CYCLE 类模式**，检出率见 ⑦评测<br>② 返回的每条环路**必须能回链到具体交易**（FR-6）<br>③ 环路内**不重复**（同一环不重复输出） |
| **实测方式** | 对注入已知环路的案例跑检测，核对 |

### FR-4 可疑团伙识别（社区发现）

| 项 | 内容 |
|---|---|
| **描述** | 在子图上做社区发现，输出紧密子图及其紧密度分数 |
| **验收标准** | ① 对注入的团伙模式，能识别出包含正确成员的社区<br>② 输出**可排序的紧密度分数**（见 FR-9） |

### FR-5 已知手法匹配（`match_patterns`）

| 项 | 内容 |
|---|---|
| **描述** | 把检测到的**结构特征转成文字**，在「已知洗钱手法模式库」中做向量检索，返回最相似的手法及其描述 |
| **输入** | 结构描述文本、`top_k` |
| **输出** | 匹配手法列表（名称、描述、相似度） |
| **验收标准** | ① 对已知模式的案例，**Top-1 匹配正确**<br>② 返回的手法描述**必须是模式库原文**（不得由 LLM 自由生成）<br>③ 相似度**可复现**（同输入同输出） |
| **实测方式** | 用注入案例跑 Top-1 命中率 |

### FR-6 原始交易查询（`get_transactions`）——**证据回链**

| 项 | 内容 |
|---|---|
| **描述** | 按账户对和时间段查询原始交易明细 |
| **验收标准** | ① 返回字段含**交易唯一标识**、金额、时间<br>② **每一条 Agent 结论都能由本工具的输出支撑**（见 NFR-3） |
| **实测方式** | 对 Agent 的每条结论做自动化溯源检查 |

### FR-7 路径查询（`trace_path`）

| 项 | 内容 |
|---|---|
| **描述** | 查两个账户之间的资金路径 |
| **输入** | 起止账户、最大长度（**≤ 8**） |
| **验收标准** | ① 存在路径时返回路径及金额<br>② 不存在路径时**明确返回「无路径」**，不是空数组（区分「没查」和「没有」） |

### FR-8 Agent 编排与**强制产出**

| 项 | 内容 |
|---|---|
| **描述** | Plan-and-Execute 编排；步数预算内自由侦查，**最后一步必须产出结论** |
| **验收标准** | ① **任何输入下都必须产出结论**（含「未发现异常」）<br>② 未产出结论的运行**必须被单独计数**，**不得折算为「无异常」**<br>③ 从输入到结论全程**可回放** |
| **实测方式** | 统计「未产出结论」占比，**目标 0%** ⚠️ |
| **⚠️ 教训来源** | 产线项目实测：15/50 案例耗尽步数未给答案，却被统计成"无异常"，**导致指标全部失真** |

### FR-9 可排序分数输出

| 项 | 内容 |
|---|---|
| **描述** | 系统对每个可疑对象输出**可排序的分数**（不是布尔值） |
| **验收标准** | ① 输出为连续分数<br>② 能按分数排序并取 Top-K<br>③ **该排序是 Precision@K 与固定召回精确率两个指标的共同基础** |
| **依据** | PRD 2.4「一个排序，两个切点」 |

### FR-10 推理轨迹

| 项 | 内容 |
|---|---|
| **描述** | 记录并展示 Agent 的每一步（规划、工具调用、观察、结论） |
| **验收标准** | ① 轨迹包含每一步的**输入与输出**<br>② 可完整回放<br>③ 与结论一一对应 |

## 二、非功能需求（NFR）

| 编号 | 需求 | **验收标准（可测）** |
|---|---|---|
| **NFR-1** | 响应时间分级 | 简单查询（侦查）**≤ 30 秒**；深度分析（多步）**≤ 2 分钟** |
| **NFR-2** | 规模 | 节点 ≥ **10 万**，边 ≥ **100 万**；在此规模下单次查询满足 NFR-1 |
| **NFR-3** | **可解释性（硬约束）** | **每条结论的溯源覆盖率 = 100%**（无一条结论找不到原始交易支撑） |
| **NFR-4** | 零 API 成本 | 全流程可用本地模型跑完；**评测期间 API 花费 = 0** |
| **NFR-5** | 可复现 | 同一输入 + 同一配置 → 同一输出（分数、排序、结论） |
| **NFR-6** | **标签隔离** | `is_laundering` 字段**不得进入任何模型输入**；有自动化检查拦截 |
| **NFR-7** | 部署 | `docker compose up` 一条命令起全栈 |

### NFR-6 为什么是硬性要求

`is_laundering` 是数据集给的**答案**。一旦它泄漏进模型输入：

- 评测分数**全是假的**（系统在"看答案答题"）；
- 而且**很难发现**——分数会异常漂亮。

**必须用自动化检查拦截**（例如：扫描所有送入模型的 prompt / 特征，命中即构建失败）。
**这条要在 CI 里有对应的检查作业。**

### NFR-3 的量化方式

```
溯源覆盖率 = 有原始交易支撑的结论数 / 全部结论数
目标值 = 100%
```

**不是"尽量"，是 100%。** 因为一条无法溯源的结论，**在合规场景下等于零价值**。

## 三、需求追踪矩阵（**面试加分项**）

**每个需求 → 由哪个设计元素满足 → 由哪个测试验证**：

| FR | 满足方式 | 验证方式 |
|---|---|---|
| FR-1 | 图谱 schema（`04-详细设计`） | 一致性脚本 |
| FR-2 | `investigate` 工具（HLD 7.5） | 计时 + schema 校验 |
| FR-3 | 环路检测算法 | 注入案例检出率 |
| FR-4 | 社区发现算法 | 注入团伙识别 |
| FR-5 | 向量模式库（ADR-0003） | Top-1 命中率 |
| FR-6 | `get_transactions` | 溯源覆盖率（NFR-3） |
| FR-7 | `trace_path` | 路径存在/不存在双向用例 |
| FR-8 | 终止条件设计（HLD 7.4） | **未产出结论占比 → 目标 0%** |
| FR-9 | 分数输出接口 | 排序可用性 |
| FR-10 | 轨迹事件契约 | 回放测试 |

> **需求追踪矩阵是很多团队的标配，也是很多候选人从来没做过的东西。**
> 面试时说「我做了需求追踪矩阵，每个需求都能指到设计和测试」，
> **这句话直接说明你有工程规范意识。**
