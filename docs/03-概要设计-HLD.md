# 03 · 概要设计（HLD）

> 回答「整体怎么设计的」。**面试问"你这个系统什么架构"，答案在这一页。**

---

## 1. 一句话架构

> **图负责「发现异常结构」，向量负责「解释它像哪种已知手法」，Agent 负责「自己决定先查什么」，最后每条结论都能回链到原始交易。**

---

## 3. GraphRAG 到底怎么工作（**最容易被问倒的一处**）

### 3.1 两种检索各管什么

| 检索 | 回答 | 为什么另一种做不到 |
|---|---|---|
| **图检索** | 「这里有异常**结构**」 | 向量比的是语义相似，**「跟 A 隔三层的账户」不是像不像的问题，是连不连得通的问题** |
| **向量检索** | 「这个结构**像哪种已知手法**」 | 图知道有这个环，但**不知道这个环叫什么、意味着什么** |

### 3.2 一次查询的完整数据流

```text
分析师问：「A 账户周边有没有异常？」
        │
        ▼
 ① Agent 规划：拆成三步
        │
        ├──► ② 图检索：取 A 的 k 跳邻域子图
        │
        ├──► ③ 图算法：在子图上跑
        │        · 环路检测  → 发现 1 条回流环
        │        · 社区发现  → 该子图紧密度 0.72
        │        · 中心度    → A 是枢纽
        │
        ├──► ④ 向量检索：把检测到的**结构特征转成文字**，
        │       去「已知手法模式库」里匹配
        │       → 最像 CYCLE（分层回流），相似度 0.81
        │
        ▼
 ⑤ 融合：拼成 LLM 上下文
      · 子图摘要（谁转给谁、多少、什么时候）
      · 算法评分（环路长度、社区紧密度）
      · 匹配到的手法描述（文献里的原文）
        │
        ▼
 ⑥ LLM 产出：结论 + 证据 + 解释
        │
        ▼
 ⑦ 证据回链：每条结论挂回**原始交易 ID**
```

### 3.3 融合发生在哪一步（**这是 GraphRAG 的定义性一步**）

**关键认知**：这里**不是**「两路检索结果做加权排序」那么简单。

**融合的真正含义是：把三种异构证据拼装成 LLM 能用的上下文**：

| 证据类型 | 来源 | 形态 |
|---|---|---|
| **结构化事实** | 图检索 | 子图（谁→谁，多少，何时） |
| **算法判断** | 图算法 | 分数（环路长度、紧密度） |
| **语义知识** | 向量检索 | 文本（相似手法描述） |

**三者互补，缺一不可**：

- 只有**结构化事实** → 模型知道有环，但**不知道该叫什么**；
- 只有**语义知识** → 模型知道各种手法的定义，但**不知道眼前有没有**；
- 只有**算法判断** → 有分数**没有解释**，分析师不敢信、也写不进报告。

## 4. 为什么不让 Agent 自由生成 Cypher？（**重要安全设计**）

一个看起来更"智能"的做法是：**让 LLM 直接生成 Cypher 查询**。

**我们不做，理由有三条：**

| 理由 | 说明 |
|---|---|
| **不可控** | LLM 可能生成全图扫描（`MATCH (a)-[*]-(b)`），**直接打破 30 秒响应约束** |
| **不确定** | 同一问题可能生成不同查询 → **违反"可复现"的非功能需求** |
| **不可审** | 生成的查询无法预先审计，**而这是金融系统** |

**替代方案：受控工具（Tool Calling）**

> Agent 只能调用**我们预先定义好、且参数受约束**的工具
> （如 `找环路(账户, 最大长度=8)`），
> **不能自由拼查询语言**。

**这条设计你有现成的经验可讲**——你的 HS Code 项目里就用了
「**MCP 封装检索工具**」而不是让模型自由查库，**是同一个思路**。

## 5. 技术选型

| 层 | 选型 | 依据（**每条都有理由，不是"流行"**） |
|---|---|---|
| 图数据库 | **Neo4j** | 规模十万节点/百万边 → 内存图库撑不住（见 6.2）；且目标公司主业是图数据库 |
| 向量库 | ChromaDB / FAISS | 已有使用经验；模式库规模小（百级），无需重型方案 |
| 嵌入模型 | **bge-m3（本地）** | 中文+英文混合；**本地跑 → 满足零 API 成本约束** |
| LLM | **本地 Ollama** | **零 API 成本是硬约束**（见 ADR 后续） |
| 后端 | Python + FastAPI | 与既有经验一致 |
| 部署 | Docker Compose | 一键起全栈（图库 + 后端 + 前端） |

---

## 6. 三条约束如何反向决定了这张选型表

| 约束 | 推出的决策 |
|---|---|
| **零 API 成本** | 必须本地模型（Ollama + bge-m3）→ 决定了推理速度 → 决定了响应时间分级 |
| **十万节点 / 百万边** | **必须 Neo4j**，NetworkX 内存图撑不住 |
| **简单查询 ≤ 30 秒** | **不能让 Agent 自由生成查询**（可能全图扫描）→ 必须受控工具 |

> **面试话术**：
> 「我先定了三条硬约束：零 API 成本、十万级节点、30 秒响应。
> **这三条反过来决定了技术选型**——必须本地模型、必须图数据库、必须受控工具。
> 我是**先定约束再选型**，不是有什么用什么。」

## 7. Agent 编排设计

### 7.1 工具粒度：分层（侦查 + 验证）✅ 已定

**为什么不用"全细粒度"**：

> 如果每个操作都是一个独立工具（取邻域 / 找环路 / 社区发现 / 中心度…），
> Agent 要把**每一步预算**花在逐个调用上，**很可能步数耗尽还没走到"给结论"**。

**这不是假想的风险，是实测过的**：

> 本人在产线根因分析 Agent 项目里踩过这个坑——
> 诊断工具粒度太细（一次只能查一个传感器），Agent 把 4 步预算全花在逐个查询上，
> **压根没走到"给结论"**，跑出 0% 检出率。
> 看起来像"Agent 能力不行"，**实际是工具设计的锅**。
> 后来把工具改成一次返回全部传感器，Agent 才腾出步数做判断。

**为什么不"全粗粒度"**：

> 做成一个大工具「分析这个账户」，Agent 就**没有编排空间**了，
> 退化成"调一次函数"——**那还要 Agent 干什么**。

**采用的方案：分层**

```text
第一层「侦查」—— 一次调用，返回汇总，帮 Agent 建立全局认识
    investigate(账户, 跳数)
      → 邻域规模 / 环路候选 / 社区紧密度 / 枢纽排名 / 时间跨度
                                │
                                ▼
第二层「验证」—— 针对可疑线索深挖，按需调用
    （具体工具集待定）
```

**这个工作方式和人一样：先扫一遍全局，再对可疑的地方深挖。**

### 7.2 设计原则：工具不是越多越好

> **每多一个工具，Agent 就多一份"选错工具"的概率，也多消耗一份上下文。**

这和第 7.1 节的坑是**同一个道理的两面**：
- 工具**太细** → 步数不够
- 工具**太多** → 选择负担大、容易选错

**所以第二层的工具要做减法，不是加法。**

### 7.3 第二层「验证」工具集 ✅ 已定（3 个）

| 工具 | 为什么保留 |
|---|---|
| **`match_patterns(结构描述)`** | GraphRAG 的**向量那一半**。砍了就退化成「纯图算法 + LLM 总结」，**就不是 GraphRAG 了**；且它是「解释」的唯一来源 |
| **`get_transactions(起, 止, 时间段)`** | 硬约束 C 的兑现手段——**每条结论回链到原始交易的唯一证据来源** |
| **`trace_path(起, 止)`** | 支持「**A 和 B 之间有没有资金往来**」这类**两点关联查询**。B 在 A 的 k 跳之外时，侦查层覆盖不到 |

**决策记录**：T7 一度考虑砍掉（因为侦查层已返回环路候选，k 跳内的情况它冗余）。
最终保留，理由是「两个主体之间有没有往来」是**真实且高频的 AML 问题**，
而它的能力边界（k 跳外）正好是侦查层的盲区。**代价是多一份工具选择负担，被接受。**

### 7.4 终止条件 ✅ 已定：步数预算 + **预留最后一步强制产出**

**问题**：Agent 可能把步数花光而**空手而归**。

**方案**：

```text
步数预算 = N
  ├─ 第 1 .. N-1 步：自由侦查与验证
  └─ 第 N 步（强制）：无论查到什么，都必须产出结论
                        「是否发现可疑 + 置信度 + 已知证据 + 还缺什么信息」
```

**关键认知（评测层面的重要性）**：

> **「什么都没找到」和「根本没给答案」是完全不同的两件事。**
>
> - 前者是**能力问题** → 可以量化（就是漏报/假阴性）；
> - 后者是**工程缺陷** → 会让**所有指标失真**，因为它同时压低检出率、
>   又虚假地压低误报率（不报警自然不会误报）。

**这不是假想的风险**：本人在产线项目里正是被后者坑过——
那一轮跑出 0% 检出率，看起来像"Agent 能力不行"，
**实际是 15/50 个案例耗尽步数、从未给出答案**。
修复后又发现其中还有"给了答案但被自己撤回"的情况，
最终把「产出结论」设计成**终止动作**才解决。

**因此**：`run.failed`（未产出结论）必须**单独计数并在评测中报告**，
**绝不能默默折算成「无异常」**。

### 7.5 工具清单总览

```text
第一层「侦查」（1 个）
  investigate(账户, 跳数)  → 邻域规模 / 环路候选 / 社区紧密度 / 枢纽排名

第二层「验证」（3 个）
  match_patterns(结构描述)          → 匹配已知洗钱手法（向量）
  get_transactions(起, 止, 时间段)   → 取原始交易（证据回链）
  trace_path(起, 止)                → 两点间资金路径（关联查询）
```

**共 4 个工具。** 每多一个就多一份"选错"的概率，所以到此为止。
