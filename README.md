# 反洗钱可疑交易分析 Agent

[![CI](https://github.com/xiaohe9/aml-graphrag-agent/actions/workflows/ci.yml/badge.svg)](https://github.com/xiaohe9/aml-graphrag-agent/actions/workflows/ci.yml)
[![Python 3.12+](https://img.shields.io/badge/python-3.12%2B-blue)](https://www.python.org/downloads/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green)](LICENSE)
[![mypy: strict](https://img.shields.io/badge/mypy-strict-blue)](pyproject.toml)

> 一个**能跑、能评、能被追问**的工业级 Agent 项目。
>
> 用 **Neo4j 图数据库 + 图算法 + GraphRAG** 检测可疑资金结构，
> **每一条结论都能回链到原始交易**。

**数据集**：[IBM AMLSim](https://www.kaggle.com/datasets/anshankul/ibm-amlsim-example-dataset)（Apache 2.0）
——官方定位就是「**生成合成银行交易数据，以及一组已知的洗钱模式，用于测试图算法**」。

> ### ⚠️ 三个必须先知道的边界
>
> **详细分析在下面各节，但只看顶部的人也该知道分寸：**
>
> | 边界 | 说明 |
> |---|---|
> | **`cycle` 召回只有 15.8%** | 真信号，但弱——不足以改变整体结论 |
> | **Agent 的 FPR 是 75%** | 根因已定位（4B 模型判断力 + 基线信号强度），**不是没查** |
> | **Agent 评测只有 10 个案例** | **所有方案对比只能当趋势看，不能当结论** |
>
> **写在这里，是因为"我知道它哪里不行"和"效果很好"一样重要。**

## 先说结论：这个项目**测出来**了什么

> **这一节是全项目最重要的部分。**
> 它记录的是**实测结果**，包括**推翻我自己假设的那些**。

### ✅ 经典金额规则：检出率 **0.0%**

| 金额分位 | 正常交易 | **涉诈交易** |
|---|---|---|
| 中位数 | 156.71 | **10.60** |

**洗钱交易的金额中位数只有正常交易的 1/15。**
所以「单笔金额超阈值就报警」这条最常见的 AML 规则，**一笔都抓不到**。

**这不是推测，是实测。**

### ✅ 检测结果

| 方法 | P@100 | P@500 | 召回 90% 需报警数 |
|---|---|---|---|
| **双检测器（本项目）** | **100.0%** | 96.6% | **53,732** |
| 单检测器（金额） | 80.0% | 95.8% | 266,669 |
| **经典金额规则** | **0.0%** | **0.0%** | 1,323,042 |
| 随机 | 0.0% | 0.2% | — |

**召回 90% 的工作量比朴素规则省 5 倍**（53,732 vs 266,669 条）。

### 📊 实测：这个好成绩来自**平凡规则**，不是结构特征

- **`fan_in` 的召回 90.7% 是「金额越小越可疑」拿到的**，结构特征没有贡献——
  **不能把平凡规则的功劳算成自己的**；
- 真正的环检测把 `cycle` 召回从 12.5% 提到 15.8%，
  **但整体仍不如不用环的方案**；
- 标注的环长 99.6% 落在 2–5，**最长 7**（这是工具契约里 `max_length ≤ 8` 的实测依据）。

> **一条能跑通的规则，不等于一条属于你的方法。**

### 🔍 数据画像**推翻了四个直觉假设中的三个**

| 假设 | 实测 | 判定 |
|---|---|---|
| 互转多 → 可疑 | cycle 19.3% vs 全图 **18.4%** | ❌ 几乎没信号 |
| 收款方入度高 → 可疑 | 121/145 vs **233** | ❌ **反了** |
| 同对账户**多笔** → 可疑 | 标注 **1–2 笔** vs 全图 **20 笔** | ❌ **反了，而且是强信号** |
| 金额大 → 可疑 | 14.91 vs 156.71 | ❌ **反了** |

> **一个信号有没有用，取决于它在这张图上的基线频率，
> 而不是取决于它在直觉上多像洗钱。**
>
> ——这一节是全项目最有价值的部分：**它证明这些结论是量出来的，不是想出来的。**

### 🔄 我**推翻了自己**的一个结论

**先前的结论**：全局环枚举不可行。

**推翻它的实测**：

| 方法 | 去重图（68,947 边）上的长度 ≤3 |
|---|---|
| `nx.simple_cycles(length_bound=3)` | **145 个环 / 120 秒触顶** ❌ |
| 本项目：集合求交 | **扫完全图 3.3 秒** ✅ |

**问题本身没那么难，是那个函数的实现有问题。**
如果当时就此打住，「第二层定向深挖」这个设计就永远只是个说法。

## Agent 层：一个**追到根因**的负面结果

**这一节比上面所有漂亮数字都更有价值。**

### 第一次评测：FPR = **100%**

在**同时含正例与负例**的样本上跑（10 个案例，两类活跃度已配对）：

```text
真阳性 TP 5   假阳性 FP 4   真阴性 TN 0   假阴性 FN 0
召回率 100%   精确率 55.6%   真实 FPR 100%
```

**Agent 把 5 个正常账户里的 4 个判成「可疑」，
剩下 1 个耗尽步数——它从来没说出过「未发现可疑」。**

### 但根因**不是「模型不行」**

追下去发现：

```text
amlsim:2454  洗钱  2 关系 181 边  最大一组 180 笔 / 金额全同 / t=0..199
amlsim:400   正常  1 关系 180 边  最大一组 180 笔 / 金额全同 / t=0..199
```

**两者结构几乎完全一样。**

> **AMLSim 的背景交易本身就高度规则**——每个账户都和固定的一组对手方反复转账。
> **所以「结构规则」在这份数据里不是信号。**
>
> **而 Agent 看到「180 笔、金额全同」时，它不知道这在全图里算多还是算少。**

**它不是判断错了，是没有基线可依。**

### 两次改进，以及诚实的评估

| | ①无基线 | ②基线做成独立工具 | **③基线内联** |
|---|---|---|---|
| 真阴性 TN | **0** | 2 | 1 |
| **FPR** | 100% | 50% | 75% |
| 召回率 | 100% | 40% | 60% |
| **步数耗尽率** | 10% | 30% | **20%** |
| **平均步数** | 3.00 | 5.90 | **3.90** |
| **平均耗时** | 80 秒 | 208 秒 | **127 秒** |

**②把 FPR 打到 50%，但步数从 3.0 涨到 5.9** —— 根因是**我把基线和事实拆成了两个工具**，
**和产线项目那个「工具太细」的错一模一样**。

**③内联之后效率回来了**（步数 5.9 → 3.9），**但 FPR 回到 75%**。
内联解决了效率，**没解决判断力**——根因在 4B 模型本身，以及检测器自己的 FPR 就很高
（`amlsim:156` 是**正常**账户却拿了 **91 分位**）。

### 📏 而决定这些数字能信多少的，是这一句

```text
TP 从 3 变到 2、TN 从 2 变到 1 —— 这种变化完全在噪声范围内。
```

> **10 个案例的样本量根本不够。上面那些数字只能当趋势看，不能当结论。**
>
> **不说这一句，就是在用不可靠的数字下结论——那比没有数字更糟。**

## 证据展示：**自包含 HTML 报告**

📄 **[`docs/demo-report.html`](docs/demo-report.html)** —— 双击用浏览器打开，**不需要任何服务**。

**为什么不是 Web 应用**：分析师要的是**能读、能引用、能放进上报材料**的东西；
面试官要的是**打开就能看**，不是"你先 clone 再起服务"。**所以可移植性比交互性重要。**

渲染的两条硬约束：

1. **三类证据必须视觉可分**（硬数据 / 有阈值依赖 / 只是"像"）——
   如果它们在报告里长得一样，读的人就会当成同等可信；
2. **「未获取到的信息」必须显眼**，单独成块并写明「请勿当作没有异常」——
   **"我看了，没问题"和"我没看"是两件完全不同的事。**

## 快速开始

```bash
# 1. 装依赖（按 lock 文件，保证可复现）
uv sync --frozen

# 2. 跑门禁（静态检查 + 单元测试，约 30 秒）
uv run python scripts/check.py

# 3. 起图库
docker compose up -d neo4j

# 4. 下数据并建图（约 4 分钟，含一致性校验）
uv run python scripts/fetch_data.py
uv run python scripts/build_graph.py

# 5. 跑完整门禁（含集成测试与标签泄漏审计）
uv run python scripts/check.py --integration

# 6. 跑检测层评测（约 30 秒）
uv run python scripts/run_detection_eval.py

# 7. 建知识库的嵌入索引（M4，约 15 秒）
uv run python scripts/build_pattern_index.py

# 8. 真跑一次 Agent（M5，约 1–5 分钟）
uv run python scripts/run_agent.py amlsim:522

# 9. 生成一份自包含的 HTML 调查报告（M6）
uv run python scripts/make_report.py amlsim:522 --out docs/demo-report.html

# 10. Agent 量化评测（M7，10 个案例约 15 分钟）
uv run python scripts/eval_agent.py --per-class 5 --dry-run   # 先看样本，不花钱
uv run python scripts/eval_agent.py --per-class 5
```

> **`--dry-run` 是刻意的**：实测第一版抽样有 3.3 倍的活跃度偏差，
> **在花 15 分钟跑评测之前，先花 3 秒检查样本。**

**Agent 层用本地 `qwen3:4b`，嵌入用 `bge-m3`——零 API 成本。**
没装 Ollama 也能跑通全流程（会**明确警告**并降级到确定性哈希嵌入）。

图库浏览器：<http://localhost:7474>（`neo4j` / `aml-agent-dev`）

## 架构

```text
⑤ 交互层    自然语言提问（分析师不会写查询语言）
④ Agent     自己拆解：取邻域 → 找环 → 匹配手法 → 解释
③ 检索融合  ★GraphRAG★ 图检索 + 向量检索 + 图算法 → 拼成上下文
② 图存储    Neo4j（132 万条边）+ 向量库
① 数据      交易流水 + 账户映射 + 模式标签
```

### 图与算法**分工**是刻意的

| 谁 | 干什么 | 为什么 |
|---|---|---|
| **Neo4j** | 存储与查询：索引、Cypher、取 k 跳子图 | 它是数据库，擅长高效定位 |
| **NetworkX** | 图算法：环检测、社区发现 | 它是算法库，实现成熟 |

> **Neo4j 自己的 GDS 插件也是这个思路**——数据库负责存储，算法另外一套。

### 分层检测

| 层 | 做什么 | 成本 |
|---|---|---|
| **第一层** | 便宜的全局信号粗筛（金额、笔数、度数……） | 可全图跑 |
| **第二层** | 定向的、有预算的环检测 | 3.3 秒扫完全图 |

**为什么必须分层**：全局环枚举在一开始被认为不可行（后来发现是库实现的问题），
而且 **98.5% 的节点属于同一个强连通分量**，所以「节点在环上」这个判断**没有区分度**。

## 标签泄漏防护（三层）

数据集给的答案 `IS_FRAUD` **绝不能出现在 Agent 能看到的地方**——
一旦"看见答案"，评测分数会很漂亮，**而且很难发现**。

| 层 | 做法 | 强度 |
|---|---|---|
| **① 不存** | 标签**不写进图**（图是特征存储，不是答案存储） | **最强** |
| **② 白名单** | 查询的 `RETURN` 子句**从白名单生成** | 强 |
| **③ 自动审计** | 扫描代码库里**全部**查询，逐条过检查 | 兜底 |

> **最强的访问控制，是不把秘密放在那里。**

第 ③ 层的关键：**自动发现查询，而不是维护手写清单**——
**手写清单会漏掉新增的查询，而漏掉的那条就是漏洞。**
而且有一个测试**反过来验证审计覆盖范围**（遍历包内所有模块，找出有查询却没被审计的）。

## 门禁

**CI 跑的命令，就是本地跑的命令**——两者都由 `scripts/check.py` 定义。
如果各写一套，迟早不一致，然后「CI 绿但本地红」会让人**不再信任门禁、开始绕过它**。

| 门禁 | 拦什么 |
|---|---|
| `ruff check` | 语法、导入顺序、可疑写法 |
| `ruff format --check` | 格式 |
| `mypy --strict` | 类型错误（**strict**，不是默认档） |
| `pytest` | 行为 |
| **标签泄漏审计** | 在 `pytest` 里，**不是可选项** |
| **workflow YAML 校验** | 用**真正的解析器**——正则会漏掉语法错误 |

最后一条是踩过坑的：上个项目里一句没加引号的 `- name: ... (not committed: 5 MB ...)`
让 GitHub **整份拒收 workflow**，于是**每次推送的每个 job 都失败，而且从没运行过**。

## 工程结构

```text
src/aml_agent/
  data/       字段契约（含标签隔离）、数据集加载
  graph/      Cypher、建图、一致性校验、**安全读路径**、标签防护
  detect/     便宜结构信号、**真环检测**、规则基线
  eval/       评测指标（含「未产出结论」单独计数）+ **Agent 量化评测**
  knowledge/  可疑模式知识库（18 条，**每条标来源**）
  embed/      嵌入层（Ollama 真实实现 + 确定性假实现供 CI）
  retrieve/   语义检索 + **融合层**（三类异构证据，带实测基线）
  agent/      工具契约、**Agent 循环（预留强制产出步）**、**基线索引**
  report/     **自包含 HTML 证据报告**
scripts/      fetch_data / build_graph / check / run_detection_eval
              build_pattern_index / run_agent / make_report / eval_agent
tests/        265 个测试（静态门禁约 17 秒跑完）
docs/         需求 → 设计 → 评测 → 踩坑 的完整文档链（18 份）
```

### 评测指标的两个设计要点

1. **系统输出必须是可排序分数，不是布尔值**——
   两个主指标（Precision@K、固定召回下的精确率）来自**同一个排序的两个切点**；
2. **「未产出结论」必须单独计数**——
   **「我看了，没问题」和「我没看」是两件事**。
   把沉默折算成「无异常」会同时**压低检出率、又虚假地压低误报率**，让所有指标失真。

### 已知但**主动决定不修**的

> **"发现了一个问题" ≠ "必须马上修"。**
> 把每个问题都当紧急事故，项目就永远做不完。

| 事项 | 为什么现在不修 |
|---|---|
| 嵌入服务降级只 `print` 警告，不走结构化告警 | 项目不是生产系统；降级路径工作正常，代码与文档都写明了 |
| 嵌入服务与图库的资源隔离 | 单机演示环境不存在争抢 |

| `cycle` 召回只有 15.8% | 已定位到原因，继续优化需要可调参数据，那是另一个里程碑 |

### 评测性能：一次由**测量驱动**的优化

```text
                  优化前      优化后      做了什么
加载边表与数据        ~31 秒     1.6 秒    多重图(132万边) → 去重图(6.9万边)
算结构特征            5.3 秒     2.1 秒    Python 循环 → 向量化；去掉多余的图参数
扫环                  2.6 秒     0.8 秒    传入去重图
构造分数              ~25 秒     4.3 秒    只对用得上的列算秩
最终对比评测(13 个)   214.7 秒    5.5 秒    numpy 向量化快路径
──────────────────────────────────────────────
总耗时               372 秒      31 秒     12 倍
```

**每一步都是先量后改的**——profile 出来才知道瓶颈在哪，
而不是"看着哪里慢就改哪里"。三个反直觉的发现：

1. **指标层的瓶颈不是算法，是数据结构**——
   `Mapping[str, float]`（130 万个字符串键的字典）每个方法都要重建一次。
   改成「一次排序 + 一次前缀和」，**14 个方法的全部指标都被覆盖**；
2. **特征计算不需要图对象**——出/入度用 `value_counts`、互转用 `MultiIndex.isin`，
   而**构建那个图对象本身要 30 多秒**；
3. **`features.rank(pct=True)` 会对 6 列各排一次序**，
   而调用方只用其中 2 列——**白算 4 列**。

> 快路径的正确性由 `test_curve_matches_the_ranking_path` 逐项锁住，
> 参数里包含 **`tie_groups=1`（全部并列）** 这个极端情况——
> **而并列正是实测踩过的坑**（全图 24 万条边分数完全相同）。
